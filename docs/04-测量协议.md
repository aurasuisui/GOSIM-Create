# 04 · 测量协议

> **每次跑实验前必读。** 这份文件里的纪律如果不遵守，所有 A/B 结论都是错的。
> 来源：2026-09-20 首日实测（非推断）+ 8 路调研中的测量方法论分析。

## 一、最重要的一条：每轮测量前重置数据库

### 实测证据

同一份**冻结**的 12306 参考实现、同一套官方测试，连跑三次：

| 次序 | 数据库状态 | 结果 | 耗时 |
|---|---|---|---|
| 1 | 初始 `db:prepare:e2e` | 131 通过 / **4 失败** | 3.6 min |
| 2 | **继承第 1 轮的累积状态** | 120 通过 / **15 失败** | 8.0 min |
| 3 | **重新 `db:prepare:e2e` 后** | **132 通过 / 0 失败** | 4.2 min |

**没有任何代码变化，第 2 轮凭空多出 11 条失败。**

> ⚠️ **第 3 行那个"132 通过 / 0 失败"不要再引用。** 该轮日志已丢失，且此后
> 四轮工具化测量从未复现过它（实测是 129 / 130 / 130 / 133）。
> 它是**一次运气好的 run**，不是"曾经达到过的干净基线"。
> 本节要立的结论是**"不重置库会污染结果"**，与 132 这个具体数字无关。

### 原因

`db:prepare:e2e` 只在第一次运行时准备数据库。之后的测试运行会命中**同一个数据库文件**，累积前面运行留下的账号、订单等状态，导致后续用例的前置条件被污染。

### 强制纪律

```bash
# 每次测量前，三件事一起做：
# 1. 停掉后端（它持有数据库连接且有内存态）
# 2. 重置数据库
cd repos/arc-bench/arc-bench/webapp/12306/project/backend
npm run db:prepare:e2e
# 3. 重启后端
PORT=3301 npm run start
```

`eval/` 里的脚本会把这个流程固化下来，**不要手工跑测试**。

## 二、其它必须遵守的操作纪律

1. **每轮之间用 `--clean` 重建工作区，不要用 `--resume`**。resume 复用 `.arc/processing_queue.json` 和已有代码，那不是独立重复。
2. **固定 `ARC_TEST_DATE`**。`tests/helpers.ts` 第 3 行：`process.env.ARC_TEST_DATE || new Date().toISOString().slice(0,10)`——**测试是日期相关的，跨天跑同一份产物结果可能不同**。注意 `arc-bench` 的 runner 默认 target 端口是 3301，而 ARC 最新提交把默认改成了 3000（`core/config.py:16`），两边要显式对齐。
3. **一次只改一处**，改动要能用一句可证伪的话描述（"把 DESIGN 阶段的 skill 从 A 换成 B"，不是"优化提示词"）。
4. **端口统一显式传**：`--target-url http://127.0.0.1:<port>`，不要依赖默认值。
5. **绝对不要并行跑两轮测量。** 见下。
6. **跑完测试要自查 `repos/` 有没有被改**：
   ```bash
   git -C repos/arc-bench status --porcelain      # 必须为空
   ```
   跑官方测试**必然**会在 `repos/arc-bench/` 里写生成物：`playwright-report/`、`test-results/`、
   以及参考实现的 `backend/database.db`（`db:prepare:e2e` 重建）。
   这些都是 **gitignored** 的产物，**`git status --porcelain` 为空即证明没有任何被跟踪文件被改动**
   —— 这是"不修改 `repos/`"这条硬规则的**可执行判据**（空输出 = 合规）。
   （2026-09-20 在 5 轮测量之后实测：空。）

### 并发事故（2026-09-20 实测，两次 run 因此作废）

两个会话在 21 秒内先后启动了 `bench.sh test`：

```
10:56:03  runner A 起跑
10:56:23  第二个 invocation 的 reset 把后端换掉了（它只杀"占着端口"的进程）
10:56:24  runner B 起跑
```

**runner A 没被杀**——playwright runner 是个客户端，**不占端口**，所以按端口找进程的 `stop_backend` 看不见它。于是 A 脚下的数据库被重置、后端被换掉，**却继续跑完**。

结果：两份日志都长得像正常结果，两份其实都不可信（已标记 `runs/*.INVALID-concurrent.*`）。其中一个在 87/135 处被静默掐断，无 summary。

**两道防线**（`eval/bench.sh` 已实现）：

**现在的防线（`eval/bench.sh`，2026-09-20 补齐了"判据只写在文档里、没写进工具"这个洞）：**

1. **互斥锁** `runs/.bench.lock` —— 同一时刻只允许一个 bench 在跑。
   `test` / `reset` / **`start` / `stop`** 全部走锁。
   （`start` 内部会调 `stop_backend`，所以它同样能杀掉正在服役的后端；`stop` 同理是在杀别人的后端。）
2. **心跳**：持有者每 20 秒更新 `runs/.bench.lock/heartbeat`。
   判"是否在跑"**优先看心跳，不看锁年龄**。PID 这条链路单独用会误判——
   实测：一轮正在跑时锁里记的 PID 已消失，旧版 `status` 判它"过期"并建议跑 `reset`，
   **而那时 `reset` 是唯一不能做的事**（当时端口被占、3 个 runner 活着、日志正在增长）。
3. **过期清理是四条件**：只有「PID 已死 **且** 无 runner **且** 端口空闲 **且** 锁年龄 > 阈值」
   才允许清理；否则拒绝并打印"疑似正在跑，需人工确认"。
   阈值 `BENCH_LOCK_STALE_SECS` **默认 7200 秒（2 小时）**——
   ⚠️ **不能设 30 分钟**：六 app 全量判分本身最坏就是 **8.0 小时**
   （478 条 × 60 秒，`playwright.config.ts` 的定义值；keep 实测 32 条 = 30.7 分钟，**失败主导**），
   加生成会远远超过，第一次跑全量就会遇到"锁被自己判过期"。
   > 📌 **2026-09-22 更正**：本处原引的"六 app 全量测试 15–30 分钟"是**参考实现全通过**时的形态，
   > 与失败主导的真实形态差一个数量级。**论证方向不变、而且更强**——阈值必须远大于单轮墙钟。
4. **游离 runner 清理** `kill_stale_runners`（`eval/kill-runners.ps1`）—— 按命令行特征找，不按端口。
5. **`status` 给一条结论行**，不再让人自己拼三条线索。判据的**锚点是锁**——
   `test`/`reset`/`start`/`stop` 全都拿锁，所以"没有锁"就等于"没有 bench 在跑"：
   | 现场 | 结论 |
   |---|---|
   | 无锁、无 runner、端口空 | 🟢 **空闲** —— 可以跑 |
   | 无锁、无 runner，但端口被占 | 🟢 **可运行** —— 那是上一轮留下的后端，无害（下次 start/reset 会接管） |
   | 无锁、但有 runner 活着 | 🟡 不确定（上一轮没退干净；下次 reset 会清） |
   | 有锁 + 任一生命迹象（PID 活 / 心跳新鲜） | 🟢 **正在跑，不要动** —— 禁止一切 bench 子命令 |
   | 有锁、无生命迹象，但端口被占或有 runner，或年龄未超阈值 | 🟡 不确定 —— 需人工确认 |
   | 有锁、无生命迹象、端口空、无 runner、年龄超阈值 | 🟡 **过期锁，可清理** |
   **旧版在有测量正在跑时会建议"跑 `reset` 清理"——那正是唯一不能做的事。**
6. **`bench.sh` 自动认领**：跑 `test` / `reset` 时自动往 `STATUS.md` 的「在飞工作」写一行，退出时清掉。
   （靠会话自觉写那一栏已失败过一次：栏里写着"无"，而当时有一轮测量正在跑。）

**仍然不要靠锁兜底。** 规则是：**动测试之前先 `./eval/bench.sh status`**，看结论行再决定。

### 🔴 哪些路径算"拿锁的测量"（2026-09-22 加，依据第二十一轮审核 D）

**判据不是"谁写的脚本"，而是"它动不动那两个共享资源"** —— **3301 端口**与**那个 sqlite 库**。

| 路径 | 起服务 / 重置库？ | 拿锁？ | 备注 |
|---|---|---|---|
| `bench.sh test` / `reset` / `start` / `stop` | ✅ | ✅ | 已完成 |
| **`eval/score_app.sh`** | ✅（构建 + 起服务 + 判分） | ✅ **已补（2026-09-22）** | 判分窗口由 `bench.sh hold <描述> -- <命令>` 包住（持锁父进程 + 心跳 + 退出释放）；`score_app.sh` 自身只认 `SCORE_LOCK_HELD=1` |
| `eval/gate0_run.sh`（含 `--reuse-app`） | ✅ | 自身不拿，**但它的判分步现在在锁里** | 它调 `score_app.sh` → 后者起持锁父进程；`acquire_lock` 的"调用方已持锁 → **继承**"分支保证不会把同一轮当"别人在跑"而拒绝 |
| `eval/test_lock.sh`（锁的行为验证） | ❌（不碰 3301、不花 token） | 用**临时** `BENCH_LOCK_DIR` + 空闲端口 | 12 条判据：无锁能拿 / 有活持有者被拒 / **继承不拒也不删祖宗的锁** / 失败退出也释放 |

> **所以 `score_app.sh` 加锁属于"测量方法"问题，不只是工具 bug**：
> 协议一直写着"锁会挡住并发"，而**实际在用的判分路径一次都没走锁**——
> 于是加锁之前那 **9 轮** keep 判分（其中 9/22 当天 **7 轮**；全部 score 轮 = 23）的并发保护，
> **只由"端口 + runner"启发式与 `STATUS.md` 在飞栏承担**。（口径见第二十二轮审核 §四.C：
> 旧文写的"15+ 轮"与 `runs/*keep-score*.log` 的实测不符——**同类手抄数字已经是第四次**。）
> **① 已做（2026-09-22）**：`score_app.sh` 的判分窗口在锁里（见上表 + `eval/test_lock.sh`）。
> **② 本表继续当规则用**：以后新增任何"起服务 + 判分"的脚本，都按同一判据判它该不该拿锁。
>
> ⚠️ **实现这一条时踩到的两个坑（都留了测试）**：
> ① **继承不能用进程树判**——WMI 父链在 Git Bash 三层嵌套下**认不出祖父**
> （实测：子进程的 parent 指向一个 `Get-CimInstance` 里查不到名字的 PID，链在第二跳断）
> → 改用**环境令牌**（`$LOCK_DIR/token` + `export BENCH_LOCK_TOKEN`，后代天然带着）。
> ② **`bench.sh test` 并不调 `score_app.sh`**（`grep -n score eval/bench.sh` 无命中）——
> 所以审核提的"子进程 PID ≠ 持有者"那条陷阱在当时的代码里**不成立**，
> 但 `gate0_run.sh` 那类调用方将来可能持锁，所以继承分支仍要留着。


**📌 锁外轮次的读数怎么记（2026-09-22 的实测口径）**

修复之前跑的那些 keep 判分轮**全部在锁之外**（这个窗口**已关闭**：2026-09-22 起 `score_app.sh` 在锁里）。
**不要把它们一律作废**，但**必须标注**，判据是：

> **锁外的读数，只有在"同一断言多次独立复现且形态一致"时才可用** —— 否则它缺并发保证。

实测（这一批恰好满足）：

| 断言 | 锁外的观测 | 一致性 |
|---|---|---|
| `REQ-2.1` **通过** | `339ms`（m2keep-official）/ `431ms`（rule5）/ `412ms`（r3a-1）/ `478ms`（r3a-2）/ `408ms`（e2-keep2）/ `443ms`（r3b-on） | **6 轮全落在 339–478ms 带内** |
| `REQ-2.1` **失败** | `11.1s`（e1b-keep4）/ `11.1s`（r3b-off） | **两轮形态完全相同**（元素不存在的等待超时） |

→ 跨小时、多次独立复现，**形态一致** ⇒ **读数可用**，但要带这句限定词：
**「锁外（`score_app.sh` 当时不拿锁），靠多次独立复现的一致性替代并发保证」**。

**✅ 判据已进工具（2026-09-20 实测验证）**：在**真实测量进行时**，
另一进程抢锁被拒（`拒绝：检测到正在运行的测量 —— 锁持有者 PID=… 还活着`），
原锁与心跳不受影响；`status` 打出 `🟢 正在跑，不要动`，证据行同时列出端口占用、活跃 runner 数、锁持有者存活。
隔离测试另外覆盖了：死 PID+心跳新鲜 → 拒；死 PID+锁年龄 30s → 拒（未超阈值）；
死 PID+无心跳+锁年龄 3h → 清（四条件齐）；活 PID → 拒；
以及结论行的五种现场（空闲 / 残留后端 / 正在跑 / 过期锁 / 不确定）。

⚠️ **测试跑完后 `bench.sh test` 不会自动停后端**（它只打印一句"完成后清场：`./eval/bench.sh stop`"）。
留着的后端会把 `status` 显示成"端口被占"——按上表它是 🟢 可运行，不是故障。

⚠️ **Windows 陷阱（别误判成"卡死"）**：`start` / `reset` / `test` 用 `nohup` 起后端，
而 Windows 下 detached 进程会继承调用者的**管道句柄**（MSYS 层的 fd 重定向管不了 OS 句柄）。
于是 `./eval/bench.sh test … | tail` 这类**带管道的调用看起来不会返回**，但它其实在正常跑。
**此时不要强杀**——先跑一次 `./eval/bench.sh status` 看结论行；或把输出重定向到文件
（`> out.txt 2>&1`）而不是管道。

## 三、噪声底线与统计方法

### 噪声底线（2026-09-20 **五轮**实测，修正先前估值）

同一份**冻结**的 12306 参考实现、同一套官方测试、**每轮前都重置数据库并重启后端**，
五轮的结果：

| 轮次 | 日志 | 通过 | 失败 |
|---|---|---|---|
| R1 | `runs/20260920T023216Z-12306-round1.log` | 129 | 6 |
| R2 | `runs/20260920T030002Z-12306-round1.log` | 130 | 5 |
| R3 | `runs/20260920T030533Z-12306-round2.log` | 130 | 5 |
| R4 | `runs/20260920T031013Z-12306-round3.log` | 133 | 2 |
| **R5** | `runs/20260920T043334Z-12306-round1.log` | **135** | **0** |

**没有任何代码变化，失败数在 0–6 之间摆动**（⚠️ 但这是**混口径**的：见下面的分组表）。R5 跑出 **135/135（3.0 分钟）**——
第一次满分（也是五轮里耗时最短的一轮：没有超时等待就没有等待时间）。

两条底线必须分开记，混在一起会得出错误结论：

**🔴 先分组，再算跨度（2026-09-20 静置序列之后确立，这是第三次修正）**

规则：**只在静置条件下比较**。`load_snapshot` 必须同时满足 `status=free`（或 `free-leftover`）
与 `runners=0`；**含污染轮次的比较一律记为无效**，不要下结论。

| 条件组 | 轮次 | 失败数 | 跨度 |
|---|---|---|---|
| **污染**（并发事故窗口 10:32–11:10，同期有两次并发 bench / 其他会话的 npm·pip 安装） | R1–R4 | 6 / 5 / 5 / 2 | **4** |
| **静置**（机器空闲、无其他会话） | R5 + Q1–Q3 | 0 / 1 / 0 / 2 | **2** |

| 口径 | 值 | 用途 |
|---|---|---|
| **静置条件下每轮失败数的波动范围** | **0 – 2（跨度 2）** | 比较"整跑通过率"时的最低可辨差异 = **2 条** |
| **会翻面的测试集合大小** | **11 条** | 做 per-test 配对时的噪声上界 |

> **先前记的"0–6（跨度 6）"是混口径算出来的假象**——它把静置的 R5 与污染的 R1–R4 混在一组。
> 分组后两组各自更窄：**污染 4、静置 2**。**"跨度 6"作废，"0–6"作废。**
> 权威数据与解读：`runs/20260920T-quiet-seq-README.md`。

⚠️ **静置样本只有 4 轮，偏薄**（`docs/04` §N 建议 ≥8–10 轮）。所以门槛带一条**自我修正规则**：
**若后续静置轮次把跨度撑到 ≥3，门槛退回 6；≥4 则退回 8。**
一次薄样本不能把门槛永久设错。

⚠️ **三个条件组不能互相比较**：污染轮次之间比、污染与静置之间比，都不成立。

### 已知会翻面的 11 条（可直接用于提高信噪比）

```
REQ-4.2.3   REQ-4.2.7   REQ-4.2.14  REQ-4.3.6   REQ-4.3.7
REQ-5.2.3   REQ-5.2.5   REQ-5.3.1   REQ-5.3.3   REQ-5.3.5
```

> 🔴 **修正（2026-09-20 R5，推翻先前结论）**：先前记的"`REQ-4.3.7` 四轮全失败 = 稳定失败"
> **已被 R5 证伪——它通过了**。所以：
> - **零稳定失败**：135 = 124 条稳定通过 + 11 条翻面
> - **"理论天花板 134/135"作废。** 实测区间是 **129–135 / 135**，满分**可达但不稳定**（五轮一次）。
> - "满分在本地套件里不存在"→ 改成"**满分不稳定**"。目标设定仍然**不追 100%**（追它不划算），
>   但**不要再引用"天花板 134"**——那会让一个真实可达的 135 被当成不可能。
> - 先前记的"132/132 干净库"因此**不再能用"运气好"一句话排除**：它与 R5 同属"满分"这一类观测。

**做 A/B 时的用法**：
1. **只在静置条件下比较**（`load_snapshot` 干净）；静置下可辨差异下限 **2 条**、**保留门槛 4 条**（见 §四）
2. 把 11 条翻面测试单列记录**成员变化**，但**不作保留依据**——它在噪声里本来就会动
3. 若某个改动声称的收益落在翻面集合内，**该结论不成立**

### 不要用整跑成功率做主指标

n=3 时，2/3 与 1/3 在统计上完全无法区分（rule of three）：

- 3/3 → 真实成功率下界约 37%
- 0/3 → 真实成功率上界约 63%

**上表四轮 129/130/130/133 就是这个问题的实例**：只看通过率会以为"稳定在 130 上下"，
但底下其实是 11 条测试在每次随机翻面。

### 正确做法：降到单条测试用例的粒度

一次 run 在 12306 上产生 135 个 pass/fail 观测，6 个 app 合计 478 个。对两个 arm：

1. 对每条测试 t，得到 (A 结果, B 结果) 四格表
2. 用**配对 McNemar 精确检验**，只看不一致的四格
3. ⚠️ **它的分辨力比想象的低得多**：配对检验的灵敏度由**不一致对**决定，不由总对数决定。
   3 次 run 合并后有 350–400 个**总对数**，但实测每对 arm 的**不一致对只有 4–8 条**。
   算例：某改动真修好 7 条，但观测到 b=9 / c=3 时 `p≈0.15`，**仍判不显著**；要显著需 `b−c≈8`。
   → **它只能确认大效应，是确认工具、不是发现工具。** 门槛见 §四（**4 条**）。

### 🔴 读数必须**连"通过的是哪几条"一起记**（2026-09-22 加）

**上面写的成员变化是"失败侧"的；通过侧同样会搬家，而且更隐蔽——因为条数不变。**

**实测（第二十轮审核那批，我逐条复核过）**：

| 产物 | 生成子集 | 通过数 | **通过的是哪一条** |
|---|---|---|---|
| `e1b-keep4` | 4 条需求 | 1/32 | **`REQ-2.7.3: Default label`（311ms）——一条不在子集里的判据** |
| `e2-keep2` | 2 条需求 | 1/32 | `REQ-2.1: Note Listing`（408ms） |

→ **通过数完全相同，通过的成员完全换了。** 只看条数会把"**分数搬家**"读成"没有变化"。
（证据：`runs/*-keep-score-e1b-keep4.judges.log` 第 16 行 `ok` vs
`runs/*-keep-score-e2-keep2.judges.log` 第 2 行 `ok`。）

**规则**：

1. **每次读数都记"通过的是哪几条"**，与失败侧对称；**比较两个 arm 时比成员集合，不比条数**。
2. **小通过数时尤其致命**：`1/32` 这种量级下，**一条的换位就是信号的整体替换**，不是噪声。
   （`N=2` 的判分重复性实验也说明这点：`r3a-1` 与 `r3a-2` 逐条一致才算"翻面≈0"。）
3. **要落到记录里**：`RunRecord.per_test_passed` / `per_test_failed`
   ——`eval/extract_run.py` 已让两者**同源**（2026-09-22）。⚠️ **旧记录里 `per_test_passed` 是 `None`**
   （`e1b-keep4` / `r3a-1` / `r3a-2` 都是），**拿旧记录做比较之前先确认字段有值**，
   否则会拿"没记"当成"没通过"。

### N 的建议

| 目的 | N | 主指标 |
|---|---|---|
| 冒烟 / 找大 bug | 2 | 能否发现 >20pp 的崩塌 |
| 决策"改动是否保留" | 3 | **通过率条数**（**静置下 4 条门槛**）；配对检验只用来确认方向 |
| 比较整跑成功率 | ≥ 8–10 | 成功率（否则不要下结论） |

## 四、改动保留的判据

**跑之前预先登记，跑之后按这个判，不许事后挑指标。**

改动分**两条轨道，判据不同**。用错轨道会把有效改动判死。

### A 轨道 —— 会改变行为的改动（提示词、生成策略、闸门、调度）

1. **通过率提升 ≥ 4 条**（= 2 × 静置跨度 2，见 §三 ；**且两轮都必须静置**——含污染轮次的比较无效），**且能被两次独立 run 复现**
2. **`pass/CNY` 不下降** —— 赛制排序口径，一等公民，不能事后补
3. 跨 app 至少 2 个不劣化；同一 app 两次独立 N 上不翻号
4. 失败原因分类发生预期迁移

**11 条翻面集合的成员变化单独记录，但不作保留依据** —— 它在噪声里本来就会动。

> **门槛为什么从 8 改成 4**（三次修正的经过，留着免得再算错）：
> ① 最初据"污染的 R1–R4"（6/5/5/2，跨度 4）定 **8**；
> ② R5 跑出 135/135 后，把 R5 与 R1–R4 混在一起得到"跨度 6"，于是以为前提失效；
> ③ **静置序列证明混算是错的**：污染组跨度 4、静置组跨度 2。
> 在静置条件下（0–2）→ 可辨差异 2 条、**保留门槛 = 2 × 2 = 4 条**。
>
> 🔴 **代价是"两轮都必须静置"**：门槛降低之所以安全，靠的是**测量条件被记录且干净**，
> 不是靠更大的余量。所以 `load_snapshot` 成了记录完整性的硬要求。

> **配对 McNemar 不是主判据。** 灵敏度由**不一致对**决定，不由总对数决定：
> 350–400 是 135×3 的**总对数**，而实测每对 arm 的不一致对只有 4–8 条。
> 算例：某改动真修好 7 条，但观测到 b=9 / c=3 时 `p≈0.15`，**仍判不显著**；
> 要显著需 `b−c≈8`。它只在极大效应时成立，**是确认工具，不是发现工具。**

### B 轨道 —— 只降成本的改动（模型路由、上下文裁剪、批量合并、缓存）

**不要用 A 的判据审它** —— 它的预期效果本来就不在通过率上。

1. **通过率落在噪声带内**（失败条数变化 ≤ 4，且 11 条翻面集合无新增成员）
2. **token / CNY 有可测下降** —— 这是唯一的主指标
3. `pass/CNY` 上升

> **M4 阶段（"只降 token，不加功能"）的所有改动都属 B 类。**
> 拿 McNemar 去审会因为分辨不出差异而把有效改动全部判死。

**任一判据不满足 → 该改动不保留。**

### 🔴 一条硬结论：在 12306 上 A 轨道现在只能测"回归"

11 条会翻面，**其余 124 条五轮里全部稳定通过**，**零稳定失败**（R5 已证伪 `REQ-4.3.7` 稳定失败）。

当前**唯一可测的通过率信号只有"回归"**：稳定的 124 条被打挂。
（原先还有"修好 `REQ-4.3.7`"这第二个信号——R5 之后它没了：没有稳定失败可修。）
**中间地带测不出来。**

→ **在噪声压下去之前，"改行为"的改动无法判断有没有用。**
→ ~~`CI=1` 重试实验是 A 轨道的前置条件~~ → **静置序列之后结论改了：不开 CI=1。**
   静置抖动本来就接近 0（0–2），开重试**不是在压噪而是在改变口径**，还会让本地口径与平台不一致。
   **改为：本地固定 `retries=0`，把 `ci_env` 记进 RunRecord**，让口径成为记录的一部分。
   （原先"必须开重试"的动机来自混口径的"失败数能摆到 0–6"——那主要是**负载**造成的，不是产物性质。）

## 五、要记录什么（RunRecord 字段）

### 🔴 记录纪律：**表格必须由脚本从记录聚合，不许手抄**

**这条是实测出来的，同一个错误已经发生过两次：**

| 处 | 手抄的数 | 记录文件实际的数 | 差额与来源 |
|---|---|---|---|
| `docs/10 §6` | 5 次 / 89,948 | **6 条 / 103,847** | 13,899 = 两次 `design` |
| `docs/12 §三`（B 组） | 8 次 / 81,862 | **9 条 / 120,326** | 38,464 = 一次 `selfcheck-review` |

**后果不是差几个数**：B 组与 A 组的成本差从 **7% 变成 57%**，判定从"B 略贵"变成"B 明显更贵"。

**根因不是手滑，是工具**：`metrics.jsonl` 的记录**没有 `run_id`**，
所以"这一次 run 花了多少"只能靠人工在时间线上挑——挑漏一次就错一次。

**三条修法：**

1. **`metrics.jsonl` 每条记录加 `run_id`**（或每次 run 写独立文件）
2. **成本表由脚本从记录聚合生成**，不接受手抄
3. 按 `PLAN §4.4` 给**两栏**：成功路径 / **含全部尝试**

> ⚠️ 而且"标定"要拿这些表当基线 —— **标在错数上等于白标**。
> 所以这张表的质量直接决定模型选型的结论。

### 身份
`run_id` / `arm_id` / `git_commit` / `git_dirty` / `change_description`（一句话、可证伪）

### 输入指纹
`app` / `requirements_sha256` / `requirements_asset_hash` / `bench_repo_commit` / `bench_spec_count` / `bench_test_count` / `playwright_config_sha256`

### 环境与模型
`model` / `visual_model` / `api_mode` / `base_url_host` / `arc_test_date`（固定值） / `node_version` / `python_version` / `port`

### 测量条件（🔴 后两个是第五轮之后新加的，用来区分"混合条件"样本）

`retries_effective` —— `CI` / `retries` 的**实际生效值**。
`playwright.config.ts` 写的是 `retries: process.env.CI ? 1 : 0`，而 `run-playwright.js` 用
`...process.env` 透传、**自己不设 `CI`**、只强制 `--workers 1`。所以**本地默认 `retries=0`**：
每一次时序抖动都被记成 failed。平台若设了 `CI=1`，则有一次重试，抖动会记成 **flaky 而非 failed** ——
**这会直接改变通过率口径**，必须记下来。

`load_snapshot` —— 跑前 `bench.sh status` 的**结论行** + 当时的 **runner 数**。

> **为什么加这两个**：第 1–4 轮（10:32–11:10）落在**并发事故窗口**内（10:56 两次并发 bench、
> 其他会话在装 npm/pip/playwright、审核会话也在执行命令），第 5 轮（12:33）是**安静时段单轮**。
> 两组样本无法用同一套说明解释（129/130/130/133 vs 135），**而旧记录里没有任何字段能区分它们**。
> 结果是跨度 4 → 6 这个变化**无法归因**——分不清是产物性质还是负载。

### 生成过程
`compile_status` / `compile_wall_clock_s` / `nodes_total` / `nodes_design_ok` / `nodes_implement_ok` / `nodes_failed[]` / `internal_green_rate`

### 可运行性（外部测试的前置）
`frontend_build_ok` / `backend_start_ok` / `backend_start_seconds` / `db_prepare_e2e_exit_code`（★ 关键，**种子缺失会在这里暴露**） / `seed_row_counts`

### 外部验证（主指标）
`tests_total` / `tests_passed` / `tests_failed` / **`pass_rate`** / `pass_rate_by_spec_file{}` / `per_test[]`（`{test_id, req_id, spec_file, ok, duration_ms, failure_class}`） / `validation_wall_clock_s` / **`noise_flip_count`**（与同产物上一轮相比翻面的条数）

`failure_class` 枚举：
`seed_missing` | `a11y_name_mismatch` | `route_missing` | `backend_5xx` | `frontend_render_error` | `assertion_text_mismatch` | `timeout` | `app_not_running`

### 成本
`requests_main` / `requests_visual` / `input_tokens` / `output_tokens` / `total_tokens` / `tokens_by_stage{}` / `tokens_by_node{}` / `cny_delta`（meter 差值） / **`pass_per_cny`**

### 产物路径
`workspace_path` / `arc_debug_log_path` / `metrics_jsonl_path` / `traceability_snapshot_path`

## 六、上界基线与它的限制

**12306 参考实现（`repos/arc-bench/arc-bench/webapp/12306/project/`）是唯一可用的 oracle。**
六个 app 里**只有它带 `project/`**，其余五个只有 requirements + tests。

- 给出天花板 —— **参考实现自己都拿不到稳定的 100%**

### 分母：12306 是 135 条测试，不是 132

`npx playwright test --list` 的权威输出：

```
Total: 135 tests in 117 files
```

**135 是分母**（117 个 spec 文件，部分文件里有多个 `test()`）。

⚠️ **踩过的坑**：本文档早先记的基线是"132/132"，那个 132 是**假象**——当时的显示过滤器写的是 `grep -E "(passed|failed) \("`，它会把 `N skipped` 行整行吃掉，于是"被跳过"伪装成了"不存在"。`bench.sh` 已修为必须带 `skipped|flaky|did not run`。

**教训**：分母对不上时，先怀疑记录工具而不是被测对象。

**它的限制**：公开快照与平台线上包有版本差（实测 ctrip 模块 125 vs 平台 133，总测试 478 vs 484）。**所以绝对数值不可依赖，只用相对提升做判据。**

## 八、成本怎么量

**代码侧结论：ARC 完全没有计量。** 全仓 grep `usage_metadata|total_tokens|cost` 零命中；`agents/model/openai_api_adapter.py:111-119` 设了 `disable_streaming: True` 和 `stream_usage: False`——非流式响应其实带 usage，只是从没被读。`tiktoken` 在依赖里但从未使用。

**三条可用路径：**

1. **平台侧（权威）**：`https://meter.arc-bench.com/user`，按 key 查人民币。**这就是评分口径本身**（榜单 Efficiency 单位 = `pass/CNY`），无需自己做换算。局限：按 key 聚合、无 per-run 粒度、有更新延迟。
2. **自建插桩（推荐）**：`agents/runtime/runners.py:363` 已经在处理 `on_chat_model_end`，**只差两行**就能读出 usage 落盘，且天然带 stage 名和 node id，可做 per-stage / per-node 归因。视觉模型是独立链路（`core/visual_analysis.py:216` 的裸 OpenAI client），需单独插一针。
3. **tiktoken 离线估算**：只适合做交叉校验。`.arc/debug.log` 里的 `model>` 被截到 1200 字符、`model-final>` 截到 2400 字符，输出侧基本无法估。

**注意**：若用 `ARC_OPENAI_API_MODE=responses` 且 base_url 非官方域名，会走 SSE 文本兜底路径（`agents/model/compatible_openai.py:57-65`），**那条路径不设 usage_metadata，本地计量可能整体为 0**。本地测量统一用 `chat_completions`。

**口径建议**：分母必须包含失败 run 的消耗。同时记三个数——`tokens_success_only`（找规律） / `tokens_all_attempts`（对齐评分） / `cny_all_attempts`（对齐 pass/CNY）。
