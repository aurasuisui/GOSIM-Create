## 一、需求 DSL 结构

加载器：`src/core/files.py:11-23`。`yaml.safe_load` 后依次尝试解包 `root:` 或 `requirement:`，最终必须有非空 `id`，否则抛错。**没有 schema 校验，没有 JSON Schema 文件。**

| 字段 | 说明 |
|---|---|
| `id` | **必填**。`ROOT` / `REQ-1` / `REQ-1.1` |
| `name` | 用于 git commit message（`core/commits.py:6`） |
| `type` | `FOLDER` / `ATOMIC`——**全仓库无任何 Python 代码读取它**（grep 零命中）。叶子/非叶子完全由 `children_ids` 是否非空决定（`phases.py:56`） |
| `description` | 长文本，**可内嵌 markdown 图片** |
| `dependencies` | 字符串 id 列表 |
| `children` | 列表，递归 |
| `scenarios[]` | `{ name, steps[] }` |
| `scenarios[].steps[].keyword` | `GIVEN` / `WHEN` / `THEN`；代码同时接受 `type` 作为别名（`pipeline.py:124-125`） |
| `scenarios[].id` / `scenario_id` | **没有 id 的 scenario 不会写入 `scenarios` 表**（`traceability.py:194-197`），只留在 requirement 行的内嵌数组里 |
| `visual_reference` | `[{image_path, analysis}]` 形态，代码支持但示例未用 |

### 参考图片的两种表达

1. **description 内嵌 markdown**（示例用这种）：`![首页](./reference/homepage.png)`。正则抽取在 `core/visual_analysis.py:163`。
2. **显式 `visual_reference` 字段**：`visual_analysis.py:152-160`。

**路径解析相对于 `requirements.yaml` 所在目录，不是工作区**（`visual_analysis.py:57-59, 171-175`）。ARC 不把需求目录拷进工作区，所以图片始终在源目录、agent 工作区里看不到，**模型只能拿到视觉分析的文本**。

## 二、`dependencies` 的真实作用

**它不影响执行顺序。** 三条实际用途：

1. **纯上下文**：`pipeline.py:193` 原样塞进 `<requirement_focus>`；`pipeline.py:394-414` 挑"相关既有接口卡片"时把 `dependencies ∩ iface.req_ids` 的接口标成 `relation: "dependency"`。
2. 记进节点会话快照（`phases.py:75`）。
3. **只影响增量重编译范围**：`_plan_requirement_sync`（`workflow.py:579-637`）里 `dependencies & changed_or_new` 把依赖方纳入 affected，再向上闭包到祖先。

**调度器完全不读它**：`_next_runnable_task`（`workflow.py:969-974`）只取列表里第一个 PENDING。**示例里依赖能成立靠的是 YAML 书写顺序，不是调度保证。**

**没有任何依赖 id 的存在性校验，也没有环检测。**

### 跨节点接口关系怎么来的（关键）

**不是从 `dependencies` 推出来的**，而是 agent 在接口里自己写 `callers` / `callees`，代码再去接口注册表反查：

- `phases.py:803-829` `_register_interface_edges`：`callers` 里的 id 若**已在 interfaces 表**→ 用其 `req_ids` 建 `cross_req` 边；`callees` 同理。
- **只有接口 id 已存在才建边**，且全仓只有这两处 `insert_call_edge` → **没有事后对账/重建 pass**。所以"先设计的节点引用后设计的接口"会**静默丢边**，边图是顺序敏感的。

## 三、队列机制

### 数据结构

```json
{ "schema_version": 2, "tree_revision": ..., "root_id": ...,
  "tasks": [...], "node_states": {...}, "last_task_id": ..., "operations": {...} }
```

- 路径 `.arc/processing_queue.json`（`QUEUE_FILENAME` :29）
- 任务项：`{task_id, node_id, phase, order, status}`，`task_id = f"{node_id}:{phase}"`（:882）
- **任务序 == 调度序**：`_build_processing_tasks`（:864-878）= `本节点 DESIGN → 递归 children → 本节点 IMPLEMENT`（后序遍历）

### 状态机

**任务**：`PENDING / RUNNING / COMPLETED / FAILED`（:40-43）

**节点**：`UNSEEN / DESIGNING / DESIGNED / IMPLEMENTING / PASSED / CONVERGED / CONVERGED_WITH_FAILED_CHILDREN / FAILED`（:45-52）

- 失败传播：节点失败 → 该节点剩余任务全标 FAILED（`_mark_remaining_node_tasks_failed` :977-980）。**但依赖方不会被阻塞。**
- `CONVERGED` 只由非叶子的 IMPLEMENT 写入；`CONVERGED_WITH_FAILED_CHILDREN` **无写入方**，死分支。

### 持久化与恢复

- **每次任务开始/结束都整份写盘**（:462, :475, :496）→ 大需求树下有 O(N²) 写放大
- 启动时 `_load_or_create_processing_queue`（:797-836）：用 `_is_compatible_queue`（:899-907）比较**base 任务 id 列表是否逐一相等**；兼容则迁移后由 node_state 反推 task status
- 中断恢复（:922-967）：RUNNING 任务改回 PENDING；非交互任务把 node_state 回退；并把 `git status --short` 前 80 行写进 node session 的 `resume_context` 交给 agent 自行判断
- **无锁、无租约、无心跳**：grep `flock|filelock|lockfile` 零命中。同一工作区并发跑两个 `--resume` 会各自整份覆写

### 重试

`_apply_retry_plan`（:982-1013）：`--retry-failed` 取所有 FAILED 节点，`--retry IDS` 取指定。按 DESIGN/IMPLEMENT 哪个失败决定回退深度（:1015-1112）。

⚠️ **陷阱**：队列不兼容时，带重试标志直接抛错（:821-824），**不带重试标志则静默新建全 UNSEEN 队列**（:825-836）。

## 四、调度改进空间（结论：不要并行）

### DFS 串行的真实代价

- **墙钟 = Σ 每个任务耗时**（严格串行）
- 单叶子最坏约 17 个会话：1×InterfaceDesigner + 1×TestGenerator + 3 层 × 最多 5 会话
- DFS 特有的代价：(a) 长尾排队——前面的难节点推迟其后所有工作；(b) **无依赖门控**——父 DESIGN 失败后子节点照跑，会对不存在的父壳做设计；(c) 与评分对齐差——评测只看 Playwright 通过率，而 DFS 按文档顺序而不是按"外部测试覆盖的节点"顺序实现

### 并行化：收益上界被卡死

已核实的硬约束（全部读到）：

1. **进程级单例 runtime**：`core/service.py:10` 模块级 `_runtime`；`core/config.py:14-17` 三个全局 + 直接改 `os.environ`；`context_pipeline` 也是模块单例（`pipeline.py:627`），`configure()` 会 `cache.clear()` 清掉所有人的缓存
2. **共享 JSON 是"整表读-改-写"，无锁**：`traceability.py:130-135, 217-223`。`write_json_atomic` 只保证单次写原子，**读-改-写不是原子的** → 两个并发写者必然丢更新
3. **每阶段 git commit 且全量**：`gitops.commit` = `git add .` + `git commit`。并行 = `index.lock` 争用 + 互相把半成品卷进 commit
4. **E2E 全局只能串行**：起服务前 `_ensure_port_released` 会**强杀**端口占用者；端口来自全局 `get_web_port()`；**评测方的 Playwright 锁死在单一基址**，所以"每 worker 一端口"对评分无效
5. 代码文件共享，无文件级锁

**结论：并行收益上界 = "设计段占墙钟的比例"，不是"节点数的倒数"。** 且省的是墙钟不是 token，而排序按 pass/CNY。**不做并行。**

**更隐蔽的一点**：`_register_interface_edges` 是增量建边、只查已存在接口、无对账 pass → **一旦重排或并行，跨节点调用边会成批静默丢失**，traceability 图反而变差。

### 真正划算的替代方案

1. **按评分权重排序**（性价比最高）：只改 `_build_processing_tasks` 的排序键——按场景数、是否有视觉参考、叶子覆盖权重排序。降低"时间耗尽时整棵子树没跑"的风险。
2. **跳过 no-op 的非叶 IMPLEMENT 回合**：现在它仍走一次任务回合 + 队列写 + 空 git commit。几百节点下是几百次白跑。
3. 若要改调度顺序：必须同步升 `QUEUE_SCHEMA_VERSION`（:30）并在迁移里做真正的任务重排，否则旧工作区会被**静默重置**。

## 五、大规模需求树先崩在哪

按"最先崩 → 最后崩"排序（推断，依据代码结构）：

1. **墙钟与 token**：几百叶子 ≈ 数千会话，每会话重发未缓存的全量上下文
2. **E2E 串行墙**：每叶子都要 build 前端 + prepare DB + 起后端 + 跑 playwright，端口固定单实例。**几百节点下最硬的物理上限**
3. **traceability 表的 O(N²) 写放大**：每次 upsert 整表读 + 整表写
4. **队列文件 O(N²) 写放大**
5. **git 历史膨胀**：2N 次 commit，每次 `git add .`（`.arc/traceability/` 入库，其他 `.arc/*` 被 ignore）
6. **上下文不是先崩点**：per-node 上下文有截断，不随树规模爆炸——这点设计得比队列层好

### 手写大 YAML 的两个静默坑

- **重复节点 id**：`store_requirement_tree` 用 dict keyed by id → 后者覆盖前者，需求表少节点；而 `_build_processing_tasks` 会为重复 id 生成**两条完全相同的 task_id**。**无任何查重校验。**
- **未知/拼错的 dependency id**：无校验 → 静默不生效。YAML 递归锚点造出环 → 直接 RecursionError。

## 五点五、⚠️ 公开基准数据里有 YAML 语法错误（6 个 app 坏了 2 个）

**2026-09-20 实测。** `arc-bench/webapp/<app>/requirements/requirements.yaml` 里有两个文件的 YAML **语法无效**，`yaml.safe_load` 直接抛 `ScannerError`。

| app | 状态 | 坏行 |
|---|---|---|
| 12306 | ✅ 可解析 | — |
| **bookstack** | ❌ `ScannerError` | L603、L645 |
| ctrip | ✅ 可解析 | — |
| **keep** | ❌ `ScannerError` | L445 |
| prestashop | ✅ 可解析 | — |
| stackoverflow | ✅ 可解析 | — |

### 错误形态：单个键相对兄弟键过度缩进

`keep` L442-448（`·` 代表空格）：

```
L442  ······-·id:·REQ-3.2            ← 键在 8
L443  ········name:·Search·by·keyword ← 8 ✓
L444  ········type:·ATOMIC            ← 8 ✓
L445  ············description:·'...'  ← 12 ✗ 应该是 8
L446  ········dependencies:           ← 8 ✓
```

`bookstack` L603 同形：`content:` 缩进 20，而同块的 `keyword:` 在 14。

**修法是对齐到兄弟层级（8），不是"再缩两格"。** 我第一版按"上一行+2"修，结果修成 10，仍然失败——因为它会被解析成上一行键的子节点。

**bookstack 修 2 行后即可解析**（ATOMIC 34 个，与预期一致）。

### 为什么这件事很重要

1. **ARC 用的就是 `yaml.safe_load`**（`src/core/files.py:14`）。喂给它这两个 app，它会**硬失败**，整个编译起不来。
2. **这两个恰好是 `arc-bench-lite/` 的两个 app**（bookstack + keep），也就是 Lite 赛道——排行榜上有真实数据的那个赛道。
3. **`PLAN.md` §7 建议"从 bookstack（34 模块）或 keep（32 模块）起步"，这两个正好是坏的。** 这条建议需要修正。

### 对管线的要求

**需求解析器必须容错，不能硬失败。** 两种做法：

- **修复式读取**：解析失败时按"键相对兄弟过度缩进"的模式做局部重对齐，重试解析
- **降级解析**：`safe_load` 失败则退回逐节点正则抽取（`id:` / `type:` / `description:` / `scenarios:`），放弃严格树结构

**不能做的**：直接 `yaml.safe_load` 然后不管异常——那样等于把 6 个 app 里的 2 个直接判死。

> 未验证：平台的线上包是否也有这两个错。公开快照与线上有版本差（见 `docs/04` §七 R1），线上可能已修。**但我们的解析器不能赌它修了。**

## 六、对我们的含义

写需求解析器时要补上 ARC 缺的东西（这些都是纯收益、零风险）：

1. **校验**：重复 id、未知 dependency、环 —— ARC 全部缺失
2. **场景索引**：`scenarios[].name` 是外部测试标题的靶子，必须建索引
3. **可访问名契约抽取**：需求文档里显式声明（见 `docs/02` §3）
4. **夹具规格抽取**：需求文档里用自然语言规定的账号/初始数据（见 `docs/02` §4）
5. **模块↔文件映射**：从第一天就记，决赛的增量编译全靠它（见 `PLAN.md` §9）
