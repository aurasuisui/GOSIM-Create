# 12 · M3b-1 前置：模型 / 成本口径标定

> **它回答的问题（`PLAN.md` §7 M3b-1 第一条，"不能跳过"）**：M3b-1 是 token 量爆炸的地方
> （1 个需求约 9 万 token → 86 个需求是另一个量级），而 **reasoning 占比取决于选哪个模型**。
> 带着错的模型铺开 = 按错的口径烧掉大部分预算。
>
> **执行时间**：2026-09-20 20:1x–20:4x。**样本**：`ticketbooking-quickstart` REQ-1（与 M3b-0 同一样本）。
> **判据**：Lab04 的 6 条验证测试。**度量口径（`PLAN.md` §7 明文）**：`token / 通过条数`，不是 token 绝对值。

## 一、结论（一句话）

**三个旋钮都测了；`reasoning_effort` 网关接受，但它与"换便宜模型"都会掉通过率——
按 `token/通过条数` 口径，目前最优仍是基线 `deepseek-chat`。**
**而且：便宜的**小样本探针**会把两个错配置都判成"更优"——端到端标定把它们挡下来了。**

## 二、第一段：小样本筛选（便宜，但**不足以定论**）

同一个代表性小任务（写一个含校验的 Express 路由文件，约 40 行），逐候选记 token 与 reasoning：

| 模型 | extra | in | out | reasoning | 占比 | **可见正文长度** | 成本指数(in+out) |
|---|---|---:|---:|---:|---:|---:|---:|
| `deepseek-v4-flash` | — | 141 | 1236 | 949 | **77%** | 856 | 1377 |
| `deepseek-v4-flash` | `reasoning_effort=low` | 62 | 483 | 52 | **11%** | **1269** | **545** |
| `deepseek-v4-flash` | `reasoning_effort=minimal` | 62 | 380 | **0** | 0% | 1125 | 442 |
| `glm-5.3-flash` | — | 70 | 411 | 0 | — | **1450** | **481** |
| `glm-5.3-flash` | `reasoning_effort=low` | 70 | 491 | 0 | — | 1562 | 561 |
| `kimi-k2.7-code-highspeed` | — | ❌ | | | | | 网关报错（名字/权限未定） |

**两个旋钮的答案（小样本阶段）**：
- **旋钮 2「网关是否认 `reasoning_effort`」→ 认。** 而且效果很大：`low` 把 reasoning 从 949 压到 52，
  成本指数 −60%，**正文反而更长**（856 → 1269 字符）——没有截断，校验要素（必填/长度/重复/201）一个不缺。
- **旋钮 1「换模型族」→ `glm-5.3-flash` 更便宜**（成本指数 481），且它**不报 reasoning 字段**、正文最长。
- 旋钮 3（`max_tokens` 截断）**本阶段不必测**：上面两个候选都没触发截断，没有可省的截断空间；
  等真出现"输出被上限截断"再测（`PLAN.md` 要求成对测）。

> ⚠️ **如果只看这一段，结论会是"`reasoning_effort=low` 是严格更优"**——而它是**错的**（见下）。

## 三、第二段：端到端确认（决定性的那一段）

同一样本、同一条管线（生成 + 验证闭环 + 构建 + 起服务 + 6 条判据）：

| # | 配置 | 网关 | 调用数 | **token（含全部尝试）** | **通过** | **token / 通过条数** | 判决 |
|---|---|---|---:|---:|---:|---:|---|
| A | `deepseek-chat`（默认） | DeepSeek 官方 | 14 | 92,158 | **6/6** | **15,359** | ✅ **当前最优** |
| B | `deepseek-v4-flash` + `reasoning_effort=low` | 比赛网关 | 8 | **81,862** | 5/6 | 16,372 | ❌ 更贵（按口径） |
| C | `glm-5.3-flash`（默认） | 比赛网关 | 9 | **53,723** | **0/6** | **∞** | ❌ 最差 |

- **B**：token 少 11%，但**少过 1 条** → 按口径反而贵 7%。
- **C**：token 少 42%（最便宜），但**一条都没过** → 口径下等于无穷。

🔴 **C 的根因我第一版写错了，2026-09-21 更正**（`PLAN.md` 更新时指出，我复核后确认它是对的）：

我原先只写了"用户名渲染成拼接文本"（`当前用户：{user.username}`）——**那只解释 1/6**。
实际证据：**6 条里有 5 条是 `page.goto: net::ERR_CONNECTION_REFUSED`**（第 1 条跑到了断言才失败 →
当时应用还活着；第 2–6 条全连不上 → **应用在第一条测试之后就死了**）。
后端日志给出了死因：

```
Error: SQLITE_ERROR: no such table: users
  --> in Database#get('SELECT * FROM users WHERE lower(username) = lower(?)', …)
    at backend/src/database/db_runtime.js:30
（未捕获的 promise rejection → Node 进程退出）
```

**真正的主因是"注册流程触发后端崩溃"**：glm 把 `CREATE TABLE IF NOT EXISTS users/sessions`
写在自己的 `auth_repository.js` 里（`auth_repository.js:34/49`），而那几条 CREATE **在使用前没跑到** →
查询先抛 `no such table` → **未捕获的 rejection 把 Node 打死**。

对照：`deepseek-chat` 那组（配置 A）也没把建表放进 `init_db.js`，但它跑通了、**6/6**——
**差别只在"运行期什么时候执行到那几条 CREATE"，静态判不出来。**

→ **这条直接决定了 M3b-1 的闸门形状**（`PLAN.md` §7 已登记）：
闭环必须能发现"**应用一起来就崩**"，而正确的仪器是**真起服务、真打一次入口（冒烟）**，
不是静态检查。见下 §四补。

## 四、这条标定真正教了什么（比数字重要）

**小样本探针会把错配置判成更优，而且理由看起来很充分。**
`low` 与小模型在"40 行代码"这个尺度上：更少的 token、更长的正文、要素齐全——
**唯一看不出来的就是"它不理解判据要什么"**。

→ `PLAN.md` §7 坚持"用 `token / 通过条数`、且要端到端"是对的；
**任何"省 token"的旋钮，都必须在 6 条判据上复测才能进 M3b-1。**

**同时暴露验证闭环的一个真实短板**：自检（review）对"显示形态不匹配"的把握**随模型而异**——
`deepseek-chat` 抓到了用户名拼接并修掉，`glm-5.3-flash` 没抓到。
→ M3b-1 铺开前，**"用户名/实体值必须单独成元素"这类约束应该进生成 prompt 的硬性清单**，
而不是只指望事后的自检（自检是发现机制，不是保证）。

## 五、对 M3b-1 的直接决定

1. **模型**：暂定 **`deepseek-chat`（DeepSeek 官方档）做本地迭代**；平台上提交时用**网关的 `deepseek-v4-flash` 且不加 `reasoning_effort`**
   —— 注意 A/B 两行**跨了网关**，不能直接当成"模型优劣"；要拿平台上真实口径，
   需要在**同一网关**上补一次 `deepseek-v4-flash`（默认 reasoning）的端到端跑（见下"未做"）。
2. **旋钮**：`reasoning_effort` **不进生成阶段**（掉通过率）；`max_tokens` 暂不动。
3. **成本基线口径**：用**本次三行的 token（含全部尝试）**当基线；`PLAN.md` 要求的"两栏"
   在本地就是"这次 run 的全部调用"（重试/修复都记在同一份 `metrics.jsonl` 里）。
4. **必须补的两件**（M3b-1 开工前）：
   - 同一网关上的 `deepseek-v4-flash`（默认）端到端一次 → 才有干净的"同模型 ± reasoning_effort"配对
   - 把"实体值单独成元素 / 退出链接形态"写进生成 prompt 的硬性清单（上面 §四）

## 八、2026-09-21：闸门第 0 条（**用比赛模型复现 6/6**）—— ❌ **不成立：只复现到 3/6**

`PLAN.md` §7 M3b-1 把这条排在最前（"最先做，最便宜，最决定性"），理由是
"**机制是模型无关的，通过率不是**"。**实测证明它是对的**：

| 配置 | 网关 | token（含全部尝试） | 通过 | 无人工构建 |
|---|---|---:|---:|---|
| `deepseek-chat`（M3b-0 基线） | DeepSeek 官方 | 92,158 | **6/6** | ✅ |
| **`deepseek-v4-flash`（平台注入的 `MODEL`）** | **比赛网关** | **156,343** | **3/6** | ✅ |

**同一份需求、同一套判据、同一条管线，只换模型 → 6/6 掉到 3/6。**
- 失败的三条仍是**同一类**：`getByText(username, {exact:true})` 找不到 → **用户名没单独成元素**
- **应用全程存活**（`ERR_CONNECTION_REFUSED` 0 次；6 条判据跑完后再探活仍 200）
  → 这次不是"应用崩了"，是**纯瞄准问题**
- 成本也更高：**156,343 token（10 条记录），其中 reasoning 89,658 = 输出的 86%**
- ⚠️ **本行数字我先前手抄错过**：曾写 **131,360**（8 次调用）——那是**中间态**。
  这一次 run 里有两轮 selfcheck→repair（`selfcheck-review` ×2、repair ×3），
  只抄前半段就低估了。**正确值：156,343 / 10 条**；
  于是 `token / 通过条数 = 156,343 ÷ 3 = **52,114**`（不是 43,787 = 131,360 ÷ 3）。
  → 这是"**成本表必须由脚本聚合、禁止手抄**"这条纪律的由来（见 §十一）。

**结论：M3b-1 不能按现在这个配置铺开。** 若铺开，最坏情况正是计划警告的那句
"**本地 6/6、平台 0/6 而不知为何**"，代价是几百万 token。

### 下一步（按依赖顺序，都在铺开之前）

1. **把判据的定位方式写进生成 prompt 的硬性清单**（不是指望事后自检）。
   现象是稳定的、可枚举的：判据用 `getByText(<值>, {exact:true})` 找**实体值**（用户名…）、
   用 `getByRole('link', {name})` 找退出入口——**值必须单独成元素、链接必须是链接**。
   `deepseek-chat` 的自检抓到了并修掉；`deepseek-v4-flash` 与 `glm-5.3-flash` 都没抓到
   → **说明它不该是"自检的运气"，而应是生成阶段的显式约束。**
2. **闭环加冒烟**（`PLAN.md` §7 那条）：起服务 → 打入口 → 确认 200；有场景标题时再跑第一个断言。
   它是本地打分脚本的一部分（agent 侧没网络、起不来）。
3. **然后重跑本条闸门**（同样本、同判据、只换模型）——过了才谈铺开。

## 九、2026-09-21 续：闸门第 0 条**重跑仍不成立（3/6）**，根因抓到并已定位到一处设计缺陷

### 重跑做了什么

按 §八 的下一步，先落了两处修复，再重跑同一条闸门（同样本 / 同判据 / 同模型 `deepseek-v4-flash` / 比赛网关）：

1. **把"定位契约"写进生成 prompt**（`STACK_CONTRACT`，每个生成块都会带上）：
   实体值必须单独成元素、导航/退出用真链接、错误进 `role="alert"`、下拉用原生 `<select>`、强度用 `<meter>`。
2. **`eval/score_app.sh`**：本地打分脚本，**第一步就是冒烟**（起服务 → `GET /` 必须 200 →
   否则**明确拒绝往下跑判据**）。它也是 `PLAN.md` §7 M3b-1"第一条"要的那根线。

### 结果：**3/6**（与修复前一样）

- ✅ **定位契约生效了**：产物里 `HomePage` 已经是 `<span>{user.username}</span>`，
  `RegisterPage` 走 `useAuth().register(payload)` + `navigate('/')`
- ❌ 但三条 happy-path 判据仍挂，失败断言仍是 `getByText(<用户名>, {exact:true})` 找不到

### 🔴 根因（两组 artifact 对照，同一个）

| artifact | 模型 | 仓储里有 `CREATE TABLE` | 结果 |
|---|---|---|---|
| M3b-0 | `deepseek-chat` | ✅ 有 | **6/6** |
| 标定组 | `deepseek-v4-flash` | ❌ **没有** | 3/6 |
| 闸门 0 组 | `deepseek-v4-flash` | ❌ **没有** | 3/6 |

两个 flash 产物的后端里，**`CREATE TABLE` 只出现在模板自己的注释里**——
`users` 表**从来没被创建过** → `SELECT … FROM users` 抛 `SQLITE_ERROR: no such table` →
route 把它吞成 **500** → 注册永远不成功 → 用户名永远不出现 → 那三条判据必挂。
（`glm-5.3-flash` 那次的同款缺陷更凶：未捕获的 rejection 直接把 Node 打死。）

**所以闸门第 0 条不过的原因不是"瞄准"，而是"应用的功能根本没跑起来"。**

### 我在这上面犯的一个错，纠正一下

我早先做过一版静态检查"SQL 用到的表有没有被 CREATE"——**它是对的**（能正确区分上表三组）。
但我随后收紧成"必须建在 `init_db.js` 里"，那版**误报了 M3b-0**（它建在仓储模块里、照样 6/6），
**于是我把整个检查撤掉了——撤错了**。

正确做法本该是**放宽判据而不是删掉检查**。现在函数与判据说明已恢复到 `verify/l1.py`，
但**暂时没接进闸门**：恢复后它仍误报（**同样的正则单独跑是对的，in-function 路径上我没定位到原因**），
而**留一个会误报的检查比没有更糟**——它会把假发现喂给定向修复。→ **待修项，已标注在代码里。**

### 顺带发现：验证闭环在比赛网关上**不稳**

重跑时 `selfcheck-review` 那一步被网关**连续丢弃**（`RemoteDisconnected`，无响应），
重试 2 次后仍在等。原因合理推测：**review 的 prompt 把全部代码塞进一次请求**，
而这个模型 reasoning 很重 → 又是 M3a 那个"大请求被断连"的形态。
→ **review 也该分块**（按文件或按组），与生成阶段的分块同理。这是重跑没能完整跑完闭环的直接原因。

### 下一步（顺序已明确）

1. **让"建表"这件事可靠**（本题的根因）：要么把它变成**闸门的硬判据**（修好上面那个 bug 再启用），
   要么在 prompt 里做成**不可跳过的显式产物**（例如要求单独输出一段 schema 文件、由管线落位）。
2. **把 review 分块**（消除网关断连，闭环才能跑完）。
3. 然后**第三次跑闸门第 0 条**——过了才谈 M3b-1 铺开。

## 十、2026-09-21 续：两个闭环缺陷的处理（计划把它们列在最前）

### ① `check_db_tables` 的 bug —— **已修并回归通过**

计划把根因定位出来了（我上一轮没找到，是因为我按"函数被定义两次"去猜）：

```python
used    |= {(m.group(1).lower(), rel) for ...}   # (表名, 文件) —— 元组
created |= {m.group(1).lower() for ...}          # 只有表名 —— 字符串
used - created        # 元组集合 − 名字集合 = 永远不消掉任何元素
```

**所以五个产物返回的是同一批 4 条**。修法两处：
1. `for table, rel in sorted((t, r) for t, r in used if t not in created)`
2. **匹配前先剥 JS 注释**（`seed_db.js:15-16` 的 JSDoc 里写着 `FROM tests`，被当成 SQL 读了）

**回归（`PLAN.md` 给了预期值，5/5 全对）**：

| 产物 | 预期 | 实际 |
|---|---|---|
| `m3b0` | 0 | ✅ 0 |
| `m3b1-low` | 0 | ✅ 0 |
| `m3b1-flashdef` | 含 `users`/`sessions` | ✅ `['sessions','users']` |
| `m3b1-gate0b` | 含 `users`/`sessions` | ✅ `['sessions','users']` |
| `m3b1-glm` | 0 | ✅ 0（它的毛病是**执行顺序**，静态判不出——与计划预测一致） |

**意义**：这条闸门现在能**在生成阶段**就拦住"从没建表"，不必等到注册接口 500 或 Node 被杀。
（它此前一直在修「幻影」——每条假发现 = 一次全量重发，而闭环占 65% 的 token。）

### ② 「大请求被网关丢」→ **客户端规则已立**

`pipeline/generate/llm.py` 新增：
- `RequestTooLarge` 异常 + `MAX_REQUEST_CHARS`（默认 24000 字符，`PIPELINE_LLM_MAX_REQUEST_CHARS` 可调）
- 超预算 → 直接抛，附"请按语义分块"的提示
- **"请求偏大 + 被断连"不再重发同一个大请求**，直接抛"该分块"

⬜ **尚未做**：`selfcheck.review` 本身还没按文件分组。预算与规则已就位，分组是下一步——

## 十三、2026-09-21（第三段）：§4.1 第 5 条规则落地 + keep 重跑

### 十三.一 为什么是这条规则

keep 那 31 条失败**全是"名字/角色对不上"**（`Toggle sidebar`×14 / `complementary`×7 / `Notes`×7 /
`Note editor`×6 / `List view`×6 / `Title`×5 / `Search`×4 / `Settings`×4）——
不是崩溃、不是连接问题（`ERR_CONNECTION_REFUSED` = 0）。而四个散文式 app 的**交互单元空转率**
是 18–50%（keep 40%）。所以第 5 条规则既是**闸门**，更是**生成 prompt 的靶子来源**。

### 十三.二 实现（`reqcompile/prose.py` + 三处接线）

- **位置约束**（裁定约束 1）：只抽祈使宾语位 / 角色名词位——
  `Click the X link`、`fill in the X field`、`the X button`、`Structure` 名词位。
  动词表**带屈折变化**（`clicks/clicking/presses/…`）——踩过 `\bclick\b` 的坑。
- **输出 (role, name) 对，并支持纯 role 目标**：`sidebar` → `complementary`、
  `note editor` → `dialog`。keep 的 `getByRole('complementary')`×7 **只要该角色存在、不要名字**，
  这一类是可直接命中的。
- **L1 分两类**（裁定约束 3）：引号/规则式 → 精确名、驱动修复；散文式 → `check_prose_names`
  **只告警**（`soft_findings`：不进 findings、不影响 passed、不驱动修复）。
  实测：3 条不存在的散文靶子 → `passed` 仍 True、3 条都进 soft。
  **为什么必须这样**：散文抽取会把 `0 results`、`count` 这类词捞进来，一旦驱动修复，
  生成阶段会**烧 token 追幻影名字**，而赛制按 `pass/CNY` 排序。
- **生成 prompt 分两块**：**必须逐字兑现**（引号式）与**从散文抽出的目标（尽力做完）**，
  后者标注"名字按你判断取最贴近的"——避免当成逐字契约。

### 十三.四 精度（裁定约束 2：必须同时报精度）

人工过 20 条后 precision ≈ **55%**，junk 三类可修，已修：
1. **冠词交替顺序错了**：`(?:the|a|an)` 里 `a` 先匹配 → 把 `an "X"` 吃成 `n "X"`
   （`'n "Action undone" notification'`）。改成 `(?:an|a|the)`。
2. **引号碎片**（`'exactly "Note trashed'`）——那是引号式规则的活，散文规则一律不收。

### 十八.4 🟡 D：`score_app.sh` 现在**在锁里**跑（两条入口都验过，且当场抓到两个坑）

- **事实核对（先验陷阱存不存在）**：`grep -n score eval/bench.sh` **无命中** → `bench.sh test`
  **不调** `score_app.sh`，所以审核说的那条"子进程 PID ≠ 持有者 → 被拒"在**当前代码里不成立**；
  `gate0_run.sh` 会调它两次，且**自己不持锁**。
- **实现**：新增 `bench.sh hold <描述> -- <命令>`（拿锁 + 心跳 + 退出一律释放），
  `score_app.sh` 开头 `exec env SCORE_LOCK_HELD=1 … hold …` 把**判分窗口**包进锁里；
  `acquire_lock` 增加"**调用方已持锁 → 继承**"分支（不重复拿、不释放）。
- 🔴 **继承判据不能用进程树——这是实测出来的**：第一版走 WMI 父链
  （`Get-CimInstance … ParentProcessId` 逐级上溯），三层嵌套下**认不出祖父**：
  子进程的 parent 指向一个 **WMI 里查不到名字**的 PID，链在第二跳就断
  （实测输出 `chain: 12052 (bash.exe) -> parent 26304 ()`）。
  → 改成**环境令牌**（拿锁时写 `$LOCK_DIR/token` 并 `export BENCH_LOCK_TOKEN`，后代天然带着它）。
  **如果没写这个测试，这段会以"看起来对"的形态留在代码里。**
- **验证**：`eval/test_lock.sh`（新，零 token、不碰真实锁/端口）—— 12 条判据全绿：
  ①无锁能拿、退出释放 ②有活持有者时**被拒且不破坏原锁** ③**继承不拒、不删祖宗的锁**
  ④`score_app.sh` 实际入口走的是持锁父进程、失败退出也释放。
- 附带收益：判分轮现在**自动认领「在飞工作」栏**（此前 9 轮 keep 判分全靠手写）。
