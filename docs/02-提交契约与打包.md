> 写生成器之前、打包之前必读。这里每一条都是硬契约，**违反大多会静默失败**，不会给你明确报错。
> 来源：平台 API 文档（`raw/ARC-Bench_平台_中文.txt`）+ ARC 源码 + `arc-template` 真实模板文件。

## 一、提交包的结构

### 规则

```
bundle.zip
├── main.py                    ← 必须在第一层
├── requirements.txt
├── ...（其余包目录）
```

- **zip 第一层必须直接是 `main.py`**。不是 `src/main.py`，不是 `submission/main.py`。
  生成方式：**在 `src/` 目录内部**执行 `zip -r ../bundle.zip .`，不是 `zip -r bundle.zip src`。
- **zip 根不能有 `package.json` / `index.js` / `index.ts`**。平台文档：*When `package.json` exists, the runner installs Node dependencies before invoking the agent*——放了会把入口切到 Node 路径。
- 不塞 `.env`（bundle 里 `.env` 的加载路径会指向上一级，且平台注入的环境变量优先级更高）。
- 不要有 `.git/`、`node_modules/`、`__pycache__/`、`*.egg-info/`、`*.db`、`.arc/`、`workspace/`。

### 入口约定（平台文档原文）

> Every uploaded agent is started with the same fixed CLI shape. Python submissions use `main.py` and `requirements.txt`.

云端会**先按 `requirements.txt` 装好 Python 依赖再执行**（这一阶段有网络），agent 真正开始跑之后**没有网络**。

### 环境变量契约（比 CLI 参数更可能是平台的实际用法）

`arcbench_agent_runtime/context.py:26-55` 读这些：

```
ARCBENCH_OUTPUT_DIR / ARCBENCH_PROJECT_DIR / ARCBENCH_TEMPLATE_DIR
ARCBENCH_RUNNER_EVENTS_PATH      （默认 .arc/runner-events.jsonl）
ARCBENCH_TRACEABILITY_DIR        （默认 .arc/traceability）
```

**这些变量的存在强烈暗示平台靠环境变量而非 CLI 参数传工作区。** 稳妥做法：`main.py` 同时支持 CLI 参数和环境变量，优先环境变量。

### 另一个关键环境变量：`ARC_AGENT_TEMPLATES_ROOT`

`app_type_handler/base.py:18-23`：

```python
def _resolve_templates_root() -> str:
    env_root = os.environ.get("ARC_AGENT_TEMPLATES_ROOT", "").strip()
    if env_root:
        return os.path.abspath(env_root)
    return os.path.abspath(os.path.join(BASE_DIR, "..", "arc-template", "templates"))
```

**这是消除"模板该放哪个相对路径"歧义的干净办法**：设了它，模板放哪都行；不设，就必须落在 `<main.py 同级的父目录>/arc-template/templates/` 下。

自研管线自带模板时，**建议自己显式读这个变量并给出明确默认值**，不要复用 `base.py` 的解析逻辑——因为 `repos/agentic-requirement-compiler/src/arc-template/` 是空的 submodule（单独 clone 的 `arc-template` 才有内容），任何走那条解析路径的代码都会在 `../../arc-template/templates` 找不到东西。

> ✅ **已由 V5 回答（2026-09-20），不要再去跑一次探针提交。**
> 平台实际传了什么、argv 长什么样、cwd 是什么、注入哪些环境变量，全部有**原文出处**：
> 见 `docs/09-平台提交与报错记录.md` §提交二（runner spec + `[runner] Executing generation-agent:` 那两段），
> 以及 `AGENTS.md`「非显而易见的事实」里的摘要。

## 二、生成的应用必须满足的契约

从 `app_type_handler/web.py` 与 `templates/web-react-express` 逐条挖出。**违反任何一条都会静默导致 E2E 全挂。**

> 🔴 **2026-09-20 按平台实测收窄。** 提交二（`probe-v2-scaffold`）让平台把每一步都跑通了，
> 因此下表新增「谁满足」一列。**这是本节最重要的一次修订**——它把 agent 的义务大幅缩小了。
> 依据：`docs/09-平台提交与报错记录.md` §提交二（含平台 Stdout 原文）。

| # | 契约 | 谁满足（实测） | 来源 | 违反后果 |
|---|---|---|---|---|
| C1 | 输出目录必须有 `frontend/` 与 `backend/` 两个目录 | **agent** | 平台首道闸的报错原文 | 硬报错 `web template is incomplete` |
| C2 | `frontend/` 的 `npm run build` 必须成功 | **平台**（它自己装 290 包并 build） | 平台 Stdout | — |
| C3 | 产物必须是**精确路径** `frontend/dist/index.html` | **平台**（由它的 build 产生） | 平台 Stdout | — |
| C4 | `backend/package.json` 必须有 `scripts.start` | **模板**（平台自带 `/opt/arcbench/templates/web-react-express`） | 平台 Stdout | 平台起服务失败 |
| C5 | `backend/package.json` 必须有 `scripts["db:prepare:e2e"]` | ⚠️ **待确认**（尚未观测到平台是否调用它） | `web.py:623-631` | E2E 数据库准备失败 |
| C6 | backend 启动后 20 秒内 `<port>` 可 TCP 连接 | **平台**（它起服务并确认 3000 可达） | 平台 Stdout | — |
| C7 | **单端口**：backend 托管 `frontend/dist` | **模板/平台** | 平台 Stdout | — |
| C8 | 端口来自环境变量，不硬编码 | **模板**（平台起在 3000） | 平台 Stdout | 起在错误端口 |
| C9 | `playwright.config` 读 `PLAYWRIGHT_BASE_URL` | **平台**（*Preparing Playwright configuration → Using preinstalled Playwright package*） | 平台 Stdout | — |
| C10 | 数据库用 sqlite 文件，支持 `ARC_DB_FILE` | ⚠️ **待确认** | `web.py:586-598` | 测试互相污染 |

### 🔴 由此产生的三条硬结论

1. **agent 侧只需产出 `frontend/` + `backend/` 的源码 + 正确的 script 声明。**
   构建、起服务、Playwright 配置都是**平台**做的。
2. **绝对不要在 agent 里 `npm install` / `npm run build`。**
   agent 跑起来之后**没有网络**（`docs/02` §1 已述），而且平台随后会自己装一遍——
   在 agent 里做这事既不可能也浪费。
3. **用平台自带的模板，不要用我们包内的那份。**
   查找优先级 `ARC_AGENT_TEMPLATES_ROOT` → `ARCBENCH_TEMPLATE_DIR` → 包内 `templates/`
   **正确命中了平台那份**（`/opt/arcbench/templates/web-react-express`）——
   平台模板必然与平台版本匹配，比我们包内的更安全。

**端口差异警告**（已实测核对，三处来源各不相同）：

| 来源 | 默认端口 | 证据 |
|---|---|---|
| ARC 的 `core/config.py:16` | **3000** | `--port` 的默认值 |
| 模板 `backend/playwright.config.js:3` | **3000** | `PLAYWRIGHT_BASE_URL \|\| ARC_WEB_BASE_URL \|\| 'http://127.0.0.1:3000'` |
| 模板 `backend/src/index.js:3` | 无默认 | `Number(process.env.PORT \|\| defaultPort)` |
| `arc-bench` runner（`scripts/run-playwright.js`） | **3301** | `--target-url` 的默认值 |
| ARC 的 `README.md:199` | 3000 之外的旧值 | 文档未同步最新提交 |

→ **模板本身写的是 3000，不是 3301**（这一条曾在本文档里写错）。真正的不一致是 **ARC 侧 3000 vs runner 侧 3301**，所以本地跑必须显式传 `--target-url`，不要依赖任何一边的默认值。

`localhost` vs `127.0.0.1` 是真实存在的坑（`get_web_base_url()` 用 `localhost`，但 TCP 探活用 `127.0.0.1`）。**后端应监听 `0.0.0.0`**，避免容器里 `localhost` 解析到 IPv6 `::1` 时不通。

backend/src/database/

### 模板的真实内容

`repos/arc-template/templates/` 下有四个：`web-react-express`、`web-react-fastapi`、`cli-python`、`mobile-android-java`。**我们用 `web-react-express`。**

`web-react-express/template.yaml` 声明了技术栈与各 root：

```yaml
stack:
  frontend: { framework: Vite, library: React, language: JavaScript, styling: TailwindCSS }
  backend:  { framework: Express, language: JavaScript, database: SQLite }
  tests:    { frontend: Vitest, backend: Vitest, e2e: Playwright }
preview: { html: frontend/dist/index.html, assets: frontend/dist/assets }
agent_guidance:
  ui_root: frontend/src
  api_root: backend/src/app.js
  function_root: backend/src
  db_root: backend/src/database
  e2e_test_root: backend/test-e2e
```

`backend/package.json` 的 scripts（**C4/C5 的答案**）：

```json
{ "start": "node src/index.js",
  "db:seed": "node src/database/seed_db.js",
  "db:prepare:e2e": "node src/database/prepare_e2e.js",
  "test": "vitest run --config vitest.config.js",
  "test:e2e": "playwright test" }
```

> **注意**：ARC 的 `copy_template()` 是裸 `shutil.copytree`，**不读 `template.yaml` 的 `copy.exclude`**（`base.py:87-92`）。要排除的东西就别放进模板目录。`copy.exclude` 是给平台预览用的。

## 三、外部测试的契约（这决定了我们该生成什么样的应用）

`arc-bench/scripts/audit-benchmark-tests.js` 的 `forbiddenSpecPatterns` 明令禁止测试使用：

```
page.goto(                       → 只能通过 UI 点击导航（唯一例外是 helpers 里的 page.goto('/')）
page.request. / /api/            → 禁止直连 API
localStorage / sessionStorage    → 禁止读浏览器存储
.evaluate( / .route(             → 禁止页面内部操作与请求拦截
toHaveURL( / page.url(           → 禁止断言内部 URL
.locator('.', '#', '[data-')     → 禁止 class / id / data- 选择器
```

**推论（本方案最高杠杆的一条）：**

> 外部测试只能靠「点击导航 + 可访问名/role 定位 + 可见文本断言」验收。
> **考的不是功能是否存在，是生成的应用是否暴露出稳定的 accessible name / role 结构。**

可同时变成三样东西：
1. **生成约束** —— 写进实现生成的 prompt
2. **本地静态检查** —— 扫描生成的 JSX，查每个交互元素是否有 label / role / 可访问名
3. **自动化探针** —— Playwright 爬一遍应用，验证必需的可访问名存在且场景入口可达（远比生成全套测试便宜）

官方还强制：每个 ATOMIC 需求恰好一个 spec 文件；spec 里 `// requirement: REQ-x.y` 注释必须匹配文件名；**每个 `test()` 的标题必须与 `requirements.yaml` 里该节点的 `scenarios[].name` 逐字、同序相等**。

→ **需求里的 `scenarios[].name` 就是靶子**，生成应以场景为单位组织。

## 四、种子/夹具契约（最容易被忽视的大面积失分点）

需求文档用**自然语言**规定夹具，实现必须自己播种。实测逐字段对齐：

- 测试侧 `arc-bench/webapp/12306/tests/helpers.ts`：
  `FIXTURES.registeredUser = { username:'registered_user', password:'Password123!', ... }`
- 需求侧 `12306/requirements/requirements.yaml:194`：
  *The system contains the verified account registered_user with username "registered_user", ... and password "Password123!".*

**逐字段一致。** 而测试**不使用任何私有 reset/seed API**，所以实现必须通过 `npm run db:prepare:e2e` 播种。

**漏播 = 大面积失败，且与功能实现质量无关。** 这类失败会严重污染实验信号。

→ **动作**：写夹具抽取器，从需求文档里捞账号/初始数据规格，直接生成 `seed_db.js`。低成本高收益，优先做。

`arc-bench` README 原文：*Before each benchmark run, the target implementation must initialize the accounts and domain data specified by its requirement package.*

## 五、合规红线

二次审查确实存在（讲师原话：**人工或用大模型**，主要查"钻空子 / 复制粘贴"）。

### ✅ 可以改（自由发挥区）

- 我们的管线代码全部自研
- 自建/复制模板（注意只放基础设施）
- 提示词、skill、模型选择、预算策略
- `requirements.txt` **追加**依赖

### ❌ 不能做

| 禁止 | 依据 |
|---|---|
| 修改 `main.py` 的输入输出契约 | 讲师明说"除了 main.py 外，它的输入输出你不要动" |
| 从 `requirements.txt` 删除依赖 | 讲师明说"只增不少" |
| **预置任何题目答案**：成品 `backend/` / `frontend/` / 页面组件 / 路由 / schema / 种子数据 | 二次审查 |
| 预置 Playwright 测试文件 | 外部测试是锁定的 |
| 修改或绕过评分、网关计量、token 上报 | F03 环外不变量 |
| **手工构造 `.arc/runner-events.jsonl` 事件负载** | 平台文档："Do not construct event payloads manually. Call high-level SDK methods only." |
| 硬编码题目特定的文案/路由/选择器到模板里 | 等同预埋 |
| 让 agent 运行期联网 | 讲师明说预期智能体不能上网 |

### ⚠️ 灰色地带（一律不做）

在模板里预置"业务无关但题目可能用到"的通用组件（如登录表单）——即使很通用也容易被判定擦边。**模板只放基础设施：构建脚本、DB 脚手架、静态托管、测试配置、端口/env 处理。零业务语义。**
