## 一、为什么成本是主线

榜单实测（ARC-Bench-Lite，9/19）：

| 队伍 | 通过率 | Token | Efficiency (pass/CNY) |
|---|---:|---:|---:|
| LGD UBIC | 100 | 0.00M | 7,692,307.69 |
| Inner Guide | 100 | 1.50M | 526.22 |
| JustSoSO | 100 | 44.19M | 8.88 |
| 非常队 | 97.0 | 21.25M | 5.42 |

**同样 100% 通过率，Efficiency 差五个数量级。唯一变量是 token。**

Smoke 榜更刺眼：官方内置 ARC agent 花 **9.09M token** 拿 100%，而"睿欣达工场"用 **0.06M** 拿同样的 100%——**150 倍**。

反推单价：Inner Guide 100/526.22 ≈ 0.19 元换 1.5M token ≈ **0.13 元/M**；JustSoSO ≈ 0.26 元/M。**说明榜单前列用的都是 flash 级廉价模型——模型这一侧没有冗余空间，唯一杠杆是 token 数量本身。**

## 二、ARC 的成本结构

### 全仓只有 5 个模型调用点

| # | 调用点 | 用途 | 阶段 | 模型来源 | 频次 |
|---|---|---|---|---|---|
| 1 | `agents/interface_designer.py:73-87, 95-108` | 接口设计 + 最小骨架 | DESIGN | `MODEL` | 每叶子 1 次；有图非叶 1 次；无图非叶**跳过** |
| 2 | `agents/test_generator.py:88-102, 114-127` | 测试生成 | DESIGN | `MODEL` | 每叶子 1 次 |
| 3 | `agents/test_driven_developer.py:185-199, 211-225` | 实现 + 修复 | IMPLEMENT | `MODEL` | **循环**，每层最多 5 session × 3 层 |
| 4 | `core/visual_analysis.py:203-234` | 截图 → 前端风格 | DESIGN 前置 | `VISUAL_MODEL`，空则回退 `MODEL` | 每张新图 1 次，有缓存 |
| 5 | `app_type_handler/android.py:344-357` | 抽 Android 包名 | android 初始化 | 主模型 | **已损坏**（读不存在的 `self.interface_designer.client`），每必抛异常被吞 → 零调用。web 不经过 |

### 成本占比：TDD 是绝对大头（推断 70–85%）

原因：TDD 的 system prompt 不短、user prompt 最长（含完整 test manifest + 失败证据）、工具轮数最多（改代码 + 反复 `run_tests`）、**且是唯一会被外层 while 循环重跑的阶段**。

占比估算：TDD ≈ 70–85%，TestGenerator ≈ 8–15%，InterfaceDesigner ≈ 5–12%，视觉 ≈ 1–3%。

**需求树规模直接决定倍数**：`example/ticketbooking-demo` 是 10 节点（4 FOLDER + 6 叶子），6 个叶子全部有图。FOLDER 阶段零调用。

主赛道实测规模（`PLAN.md` §3.3 有完整表）：**665 个节点，其中 460 个 ATOMIC**，配 460 个 spec 文件 / 478 条测试。平台页面标注 468 模块 / 484 测试，属公开快照与线上包的版本差。

**这个规模 × 每节点三场会话 = ARC 的成本结构问题所在。**

### 输出 token 占比小（5–10%）

## 三、上下文放大点（省 token 的具体位置）

按量级排序：

1. **每次会话重建完整上下文，会话之间不共享消息历史**（`test_driven_developer.py:88-99, 185-208`；`runners.py:68-72`）。一个节点最多 15 次会话，每次重发一份完整 base prompt。`thread_id` 传了但**从不配置 checkpointer**（`factory.py:117-140` 未传）→ 不承载历史。
2. **接口块被发送两遍**：`<interfaces>`（`pipeline.py:491-497`）与 `### Current Interface Contract`（`pipeline.py:440-449` + `test_driven_developer.py:100-101`）内容逐字节重复。
3. **`existing_interface_cards` 无差别塞满 30 张**（`pipeline.py:66`，`max_related_interfaces = 30`）。每张含 180+220 字符截断说明 + callers/callees，≈10-12KB，每个节点的每次会话都带。
4. **测试信息重复三遍**：`test_files` 清单 + `ordered_layers`（同批路径再列一次）+ `Current Node Test Manifest`（**全部层的完整 test dict**，`indent=2`）。
5. **需求描述与场景全文无截断**：`description` 原样进 `<requirement_focus>`，场景步骤全文进 `<scenarios>`。
6. **工具结果永久驻留**：`run_tests` 输出（Unit/Integration 每段 ≤4000 字符；**E2E 是 4 段拼接，单次能到 12-16KB**）一旦进历史，本会话后续每次模型调用都要重发。`read_file` 上限 200 行。
7. **`search_interfaces` 是放大器**：整包 JSON 返回（含完整 `content`），而系统提示词鼓励在上下文不清时调用——它返回的正是 prompt 里已经有的东西。

### 固定文本实测（AST 统计字面量）

| 项 | 字符数 |
|---|---:|
| TDD 系统提示 | ≈6,254 |
| user prompt 的 Task/Scope 模板 | ≈5,190 |
| `build_stack_block` | ≈2,137 |
| `project_structure_lines` | ≈661 |
| 失败时额外加载的 `tdd-test-failure-repair/SKILL.md` | 3,642 字节 |

### 单会话量级（推断）

按混合中英文 ≈2.5-3 字符/token：base prompt ≈ **9-15k token**；单会话通常 8-20 次模型调用，读文件 + 测试输出使历史再增 20-60KB。
→ **单会话输入约 10 万 - 40 万 token**。其中"重复发送同一份 base"和"错误日志堆积"是同量级的两个最大项。

| 旋钮 | 位置 | 默认 | 方向 |
|---|---|---|---|
| `MODEL` | 三个 agent 各自 `os.environ.get("MODEL")` | `gpt-5.4`（env 缺省） | 拆成按阶段 |

| 视觉缓存 | `visual_analysis.py:185-200`；**每次全新编译删除**（`workflow.py:172`） | 有 | `--resume` 保留，新编译重付 |

**`ARC_STRUCTURED_OUTPUT_RETRY_COUNT` 是死配置**：除校验外全仓无引用。解析失败时 `extract_payload`（`runners.py:93-125`）**不重试**，直接退化成 `{"summary": 原文}`。

### Lab02 冻结基准（11 模型，temperature=0，2026-09-11）

| 模型 | 尝试 | 成功 | Direct 隐藏验证 | TDD 隐藏验证 | 平均 token |
|---|---:|---:|---:|---:|---:|
| qwen3.8-max | 5 | 4/5 | 8.3/36 | 26.0/36 | 143,575 |
| qwen3.6-plus | 5 | 3/5 | 8.3/36 | 33.0/36 | 148,316 |
| **glm-5.3** | 3 | 1/3 | 15.0/36 | **35.0/36** | **47,281** |
| **minimax-m3** | 3 | 1/3 | 15.0/36 | **35.0/36** | 227,522 |
| deepseek-v4-flash | 1 | 0/1 | 19/36 | 未取得 | — |

**三条结论：**

1. **TDD 相对 Direct 的隐藏验证提升是 3-4 倍。** 测试驱动闭环就是通过率的主要来源——这条支撑了方案的整个验证闸门设计。
2. **`glm-5.3` 是性价比冠军**：35/36 且 token 只有 `qwen3.6-plus` 的 **1/5**。批量生成的头号候选；`glm-5.3-flash` 更便宜，一起测。
3. **`deepseek-v4-flash` 的失败形态值得注意**：它的 Direct 实现拿了 19/36（比 qwen3.8-max 的 Direct 还好），但整体判为 `INVALID_TRAIN_SUITE`——**它生成的测试套件在参考实现上就红，整套流程作废**。

> **便宜模型的瓶颈不在写代码，在"从需求生成一套自洽可执行的测试"。** 这是测试闸门（`PLAN.md` §4.2）存在的直接理由。

**`qwen3.8-max` 不要用于批量生成**——基准里最贵的一档。

## 六、路由方案

### 最优策略与"直觉"相反

排名规则是"通过率过线 → 按 pass/CNY 排序"，所以不是"贵模型做难的、便宜模型做简单的"，而是：

> **默认全部用最便宜的能过线的模型；只在"同一失败指纹重复出现"时升级。**

这个信号代码里已经准备好了：`recent_failure_summary` / 失败指纹（`test_driven_developer.py:254-276`）会写进 node session，并在下一轮注入 prompt。

### 降级风险分级

| 调用 | 降级风险 | 依据 |
|---|---|---|
| 视觉分析 | **低，优先降** | 一次性风格描述，输出只进 `visual_reference`；有缓存 |
| TestGenerator | **中低** | 输出是结构化 manifest，有确定性校验；写坏的测试能在 TDD 阶段被改 |
| InterfaceDesigner（非叶 UI-only） | 低 | 非叶只出 shell/route-slot 契约 |
| InterfaceDesigner（叶子，含 DB/API 契约） | **中** | 契约决定下游全部工作，错了会在 TDD 里反复返工 |
| TDD 首个 session | **高** | 直接决定外部 Playwright 通过率 |
| TDD 后续修复 session | 中 | 已有失败证据，任务更局部，适合便宜模型 |

### 落地方式（两档）

**A 档：静态分工**（约 10 行）。给三个 agent 传 `model=`，各自读新 env（`MODEL_DESIGN` / `MODEL_TEST` / `MODEL_IMPLEMENT`，缺省回退 `MODEL`）。**管道已就绪**（`build_stage_agent(model=...)` 在 `factory.py:84, 113`），只是 `workflow.py:101-118` 构造时没传。

**B 档：失败驱动升级**（推荐，约 30 行）。在层内 while 循环里按 session 序号切换：
- 第 1 个 session → 便宜模型
- 同层第 2 个 session 起，若指纹与上轮相同（没进展）→ 换强模型重建 agent
- 指纹不同（有进展）→ 继续便宜模型

`build_stage_agent` 本来就每次重建，换模型只是换一个入参，副作用小。

**预期降幅公式**：`成本降幅 = s × (1 − r)`，`s` = 走便宜模型的 token 占比，`r` = 便宜/贵的单价比。
- A 档：s ≈ 0.15–0.20；若 r=0.1 → 降幅 ≈ 13–18%
- B 档：s ≈ 0.5–0.7；r=0.1 → 降幅 ≈ 45–63%
- **风险**：弱模型把 1 个 session 变成 3 个 session，会直接吃掉收益。所以必须用"总成本 vs 通过率"成对测量。

## 七、另一个成本项：reasoning token

**实测：一次"只回 ok"的极简调用 = prompt 88 + completion 18（其中 16 是 reasoning）= 106 token。**

推理开销是**纯额外成本**。批量生成几千次调用时会累积。

**待查**：能否通过参数抑制？还是模型固有？（注意 ARC 全仓 grep `temperature|top_p|max_output_tokens` 在模型构造路径上**零命中**——既无 temperature 也无 max_tokens 上界。**"加上限"本身就是一档可 A/B 的降本改动。**）

## 八、配套的省钱项（不改通过率，纯白拿）

1. 修 prompt 里 "budget of 10" → 与代码的 5 一致
2. 视觉分析前**本地缩放图片**。`visual_analysis.py:214-215` 把原图直接 base64 成 data URL；实测 demo 的 `homepage.png` 是 2846×2112 / 2.6MB → base64 约 3.5MB。**若网关把 base64 当文本 token 计费，单张图会变成百万 token 级灾难。** 必须用一次真实运行核对"输入 token 数 vs 图片数量"的比值
3. `--resume` 已保留视觉缓存，**评估时不要用 `--clean` / 新建目录重跑**（`workflow.py:172` 会删缓存）
4. 删掉 `android.py:344-357` 的死代码路径（零成本，但避免误判）
5. E2E 结果拼装时**通过的部分不拼**（`web.py:463-493, 1009-1047`）：build/db 通过时只留 1 行状态；backend 进程指纹压到 2-3 行或整段移除。估：E2E 工具结果 12-16KB → 1-2KB
