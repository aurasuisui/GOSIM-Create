## 三、怎么做的（`pipeline/` 的第一次 LLM 调用）

新增三个模块，**共 ~600 行**：

| 文件 | 作用 |
|---|---|
| `pipeline/generate/llm.py` | 模型客户端。**自己发 HTTP**（不走 `openai` 包）以便**逐次记录 usage**；带重试（连接层失败与 5xx/429） |
| `pipeline/generate/implement.py` | 生成本体：1 次设计 + **4 个分块**实现 |
| `pipeline/main.py` | 接线：`run_stage1` 交出需求树与 a11y 索引；`PIPELINE_GENERATE` / `PIPELINE_REQ_IDS` 控制开关与范围 |

### 为什么要"分块"（一个实测教训）

第一版是**三次调用**（设计 / 后端 / 前端）。**后端那一次被网关直接断开连接**
（`RemoteDisconnected`，无响应）。探针确认网关本身健康（小请求 3.7s、1160 字代码 6.2s），
所以是大请求特有。改成**每次只产出 1–2 个文件**的四个分块后，五次调用全部成功。

> 顺带发现：`deepseek-v4-flash` 的 **reasoning token 占比极高**（见下），
> 把 5 个文件压在一次里，输出预算很容易被推理吃光 → 上游断开。

### 分块之间的"契约对齐"

后一块能看到**前一块产物的原文**（`_side_extra`）：后端路由块带上 `auth/*`，
前端块带上 `backend/src/routes/*`。目的：让接口逐字对齐，而不是各自猜。

## 五、失败根因（逐个查清，都是可复现的）

### 5.1 构建失败：一处相对路径写错（生成的机械错误）

`AuthContext.tsx` 里 `import ... from '../api/auth'`，而该文件在 `src/features/auth/` 下，
到 `src/api/auth.ts` 需要 `../../api/auth`。**改一处即构建通过**（96 模块，1.75s）。

### 5.2 🔴 上游模板 bug：`initializeDatabase()` 第二次调用起返回 undefined

**这不是我们生成的错**（生成器甚至被禁止改 `backend/src/database/`）。证据：

- 我们的模板副本与 `repos/arc-template/templates/web-react-express/` **当时逐字节相同**
  （⚠️ **此后包内副本已同步这一行修复，现状差异仅 `+ return database;`**——
  下一个会话 `diff` 到这一行时不要以为模板被随意改过）
- 服务层直呼复现：`TypeError: Cannot read properties of undefined (reading 'exec')`
  at `db_runtime.js:54` ← `execOnDatabase(undefined, sql)`

**机制**：`init_db.js` 里
```js
if (initPromise) { return initPromise; }     // ← 第二次调用走这里
const database = getDb();
initPromise = (async () => { ... })();       // ← 这个 IIFE 没有 return → resolve 成 undefined
...
return database;                             // ← 只有第一次调用能走到
```
而 `db_runtime.js` 的 `run/get/all/exec/withTransaction` **全都** `await initializeDatabase()` 当句柄用。
`app.js`（模板自己写的）启动时已经调过一次 → 之后**任何**查询助手调用都会崩。

**已修，并且修在"产物"上而不是只改自己的副本**：新增 `pipeline/generate/scaffold.py` 的
`apply_known_fixes()` —— 幂等、模式可判定、修复后日志留痕。
**为什么必须修在产物上**：脚手架优先用**平台自带**的模板（`/opt/arcbench/templates/…`，V5 实测），
只改我们包里的副本修不到平台那份。

### 5.3 前端三处接线/瞄准缺陷（生成的质量问题，非能力问题）

| # | 缺陷 | 证据 |
|---|---|---|
| a | `App.tsx` 渲染 `<RegisterPage />` **不传 `onRegistered`** | 组件里 `onRegistered?.()` 成了空操作 → 注册成功后**不跳转** |
| b | `RegisterPage` 直接 `apiClient.post('/auth/register')`，**不走 context 的 `register()`** | 即使跳转，登录态 state 也不会更新 |
| c | `HomePage` 渲染 `Welcome, {user.username}!` | 判据用 `getByText(username, {exact:true})` 要求**某元素完整文本就是用户名** → 永远匹配不到 |

**手工最小修复这三处 → 6/6。** 三处合计改动不到 30 行。

## 六、成本（第一次有真实数字）

| 项 | 值 |
|---|---|
| 调用次数 | **5**（1 设计 + 4 分块；第 2 次跑的"设计"复用了落盘缓存） |
| token | **89,948**（in 21,417 / out 68,531） |
| **其中 reasoning** | **59,972 = 输出 token 的 87%** ⚠️ |
| 墙钟 | 431 秒（生成）＋ 构建/起服务/测试约 1 分钟 |
| 产物 | 9 个文件（后端 4 / 前端 5） |

**⚠️ 这是本阶段最重要的成本发现**：`deepseek-v4-flash` 的**推理 token 是主要成本**，
而且它**同样计费**（`PLAN.md` §11 V4 已实测）。压缩成本的第一杠杆不是"少写代码"，
而是**抑制 reasoning**（换模型 / 调参数）。

**旁证**：同一次"只回两个字"的调用，
比赛网关计 **88 in + 9 out = 97** token，DeepSeek 官方 API 计 **9 in + 1 out = 10** token。
口径差异很大，**先用官方 API 做本地迭代、把比赛额度留给真实提交**（用户 2026-09-20 提供了测试 key）。

## 七、对 M3b 的含义

1. **能力这一关过了**（第一行），所以**不需要翻 §2 到 ARC 主线**。
2. **要补的不是"更强的生成"，而是"生成后的自检与定向修复"**：
   - 5.2 那种上游 bug → 已经能确定性修补（`apply_known_fixes`），**但需要"跑一次构建/起服务"来发现**
   - 5.3 那种接线缺陷 → **正是 `PLAN.md` §4.2 的 L1 闸门要抓的东西**
     （"场景入口是否可达、声明的可访问名是否都在"——本例中 `getByText(username)` 与
     `a[href="/register"]` 都属于此类）
3. **下一步顺序**：先做 **L1 闸门（可执行性）**，让机器自动发现 5.1/5.3 这类问题；
   再把 `apply_known_fixes` 扩成"模板体检"；最后才谈把通过率从 6/6 铺到 86 个模块。
4. **样本量提醒**：M3a 是 **1 个需求 / 6 条测试**。它证明"机制成立"，
   **不证明"铺到 86 条还能保持"**——那正是 M3b 的问题。
