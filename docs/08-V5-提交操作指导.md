## 一、上传前的前置检查（**缺一项就别传**）

| # | 检查 | 怎么做 | 本次实测值（2026-09-26） |
|---|---|---|---|
| 1 | **包与当前代码逐字节一致** | 见下方脚本（比 `output/bundle.zip` 与 `pipeline/`） | **57 个文件 / 0 不同 / 0 缺失** ✔ |
| 2 | **红线 9：包内零题目特定字符串** | `python eval/check_bundle_strings.py --zip output/bundle.zip` | **0 处命中** ✔ |
| 3 | **包根直接是 `main.py`**（不套一层目录） | `python -c "import zipfile;print('main.py' in zipfile.ZipFile('output/bundle.zip').namelist())"` | `True` ✔ |
| 4 | 工作区 **`git status` 干净** | `git status --porcelain`（应为空） | ✔ 空 |
| 5 | **记住这一版对应哪个提交**（写进 Submission name） | `git log -1 --format="%h %ad %s"` | **`90180c3`**（2026-09-26 10:11）<br>`重打包：清掉新代码注释里的题目特定字符串` |

**逐字节脚本**（照抄即可；`0 不同 / 0 缺失` 才算过）：

```bash
python - <<'PY'
import hashlib, pathlib, zipfile
z = zipfile.ZipFile('output/bundle.zip')
names = sorted(n for n in z.namelist() if not n.endswith('/'))
bad = [n for n in names if not (pathlib.Path('pipeline') / n).is_file()
       or hashlib.sha256((pathlib.Path('pipeline') / n).read_bytes()).hexdigest()
          != hashlib.sha256(z.read(n)).hexdigest()]
print(f"包内 {len(names)} 个；不同/缺失 {len(bad)} 个 {bad}")
PY
```

⚠️ **一条刚踩过的经验**：`./eval/package.sh` **自己会跑红线闸门** —— 本次它**当场抓到**新写的注释里
有 4 处 app 名（`pipeline/` 会进包，`docs/` 不进包）。按 `AGENTS.md` 红线 9，**"全仓"读作"提交包"**：
`pipeline/` + `templates/` 里不许有题目特定字符串，**事实（app 名 + 数字）留在 `docs/` / `runs/`**。

## 二、平台怎么调我们（V5 实测；逐字原文见 `docs/09`）

```
python3 /workspace/submission/main.py <需求目录> --output-dir /workspace/template
```

- 需求是**位置参数**，而且是**目录**（不是文件）；输出用 **`--output-dir`** 长选项。
- 输出目录 **`/workspace/template` 同时是 project_dir / template_dir**；
  `ARCBENCH_RUNNER_EVENTS_PATH` / `ARCBENCH_TRACEABILITY_DIR` 指向它下面的 `.arc/`。
- 平台注入 **`MODEL` / `VISUAL_MODEL`**（与表单里的两个字段同名），我们管线内部的分层路由不受影响。
- 容器是 **Python 3.12**（本地 3.13）→ 依赖与语法都要按 3.12 兼容。
- 🔴 **平台自带模板**（`/opt/arcbench/templates/web-react-express`），并且**平台自己**
  `npm install` + build + 起服务（实测 frontend 装 290 包 / 16 秒）。
  → **agent 里不要 `npm install`、不要 build**：agent 跑起来之后**没有网络**。

## 三、每 run 的**第一道闸**：必须产出 `frontend/` + `backend/`

缺了报 **`web template is incomplete: expected frontend/ and backend/ directories`**，
**六个任务会一起挂在这一条上**（V5 第一次提交就是这个形态：agent 只跑需求编译、从不产出骨架）。
落地逻辑在 **`pipeline/generate/scaffold.py`**。

## 四、提交步骤（照做即可）

主赛道页面：**https://arc-bench.com/competitions/arc-bench-web**（右侧栏「Save an agent snapshot」）

| 字段 | 默认值 | 说明 |
|---|---|---|
| 语言选择 | **Python 已选中** | 另两个是 JavaScript / TypeScript，**不要动** |
| 拖放区 | — | 文案：*Drop your agent code here. Keep the runtime entrypoint at the ZIP root.* |
| Submission name | 空 | **建议写成"能认出对应哪个提交"**，例如 `six-apps-90180c3` |
| Base URL | `https://api.arc-bench.com/v1` | 保留 |
| **API Key** | 空（Required） | **填工作区 `.env` 里的 `ARC_API_KEY`**（见 §六 的 A1） |
| Model | `deepseek-v4-flash` | 保留 |
| Visual Model | `deepseek-v4-flash-vision-exp` | 保留 |
| Save submission | 禁用 | 选好文件 + 必填项齐了才会亮 |

1. 打开上面的页面，确认语言是 **Python**；
2. 把 `output\bundle.zip` **拖进** "Drop your agent code here"；
3. **Submission name** 填能认出提交的（建议带 short hash）；
4. **API Key** 填 `.env` 里的 `ARC_API_KEY`；
5. **Base URL / Model / Visual Model 不要动**；
6. 点 **Save submission**；
7. 🔴 **然后逐任务跑满 6 个**（见 §六：同一份提交必须跑完全部 6 个任务才计聚合分）。

## 五、提交后怎么核 + **日志阅读顺序（四问）**

**怎么看**：`https://arc-bench.com/competitions/arc-bench-web`（需登录）→ 右侧栏 **History (N)** →
展开某次提交 → 每个任务一行 **Open run** → run 页先看 **Stage 1/2/3** 时间线，再看底部 **Stdout**
（有 `Refresh logs`），同页还有 **Download code**。

**四问，按顺序问**（每一步都有可 grep 的原文，见 `docs/09`）：

| # | 问什么 | 日志里找 |
|---|---|---|
| ① | **生成跑完没** | `generation-agent exit code: 0` |
| ② | **后端起来没** | `Template application is reachable on http://127.0.0.1:3000` / `Deploying generated application → reachable …` |
| ③ | **测试跑起来没** | `Executing tests with 1 workers → Test progress 0/86 …` |
| ④ | **结果是什么** | `Playwright results parsed: passed=…, failed=…, score=…` |

⚠️ **看到"六个任务报同一个错"→ 查公共环节**（骨架、构建、起服务、入口契约），
**不要去翻某个 app 的需求** —— 两次提交都是这个形态。

## 六、计分与榜单（决定"这一跑值不值"）

- 主赛道计分要求**同一份提交跑完全部 6 个任务**（表单原文：*This snapshot is shared by all competition
  tasks. Choose a task afterwards to run it.*）。
- 🔴 **0 通过 = 不上榜 = 与"没提交"等价** —— 地板不是"能跑完"，是"至少有一部分功能可用"。
  （V5 第二次提交：6 个任务的 86 条测试**全部跑起来**、平台每一步都成功，但 **0/86 → 不在榜上**。）
- **榜单两级**：**Senior**（平均通过率 ≥80%，展示全部指标）/ **Junior**（<80%，只展示排名 + 用户 + 通过率 + 覆盖度）
  → **进 Junior 就是"有分"**。
- ⚠️ 前 6 名里多个队伍 **token ≈ 0 / runtime ≈ 0 却拿 80–100%** —— 计量口径存在我们还不理解的机制，
  **在搞清之前不要据此调整成本策略**。

## 七、这次跑要**记录回来**的三件 + 要回答的三个问题

**记录三件**（按 `docs/09` 的统一格式：**报错原文 + 诊断 + 平台侧事实**，别只贴我方的解释）：

1. **报错原文**（逐字，含 `Your run failed: …` 那一行）；
2. **平台侧事实**：调用的 argv、注入的环境变量、输出目录、模板路径、**构建与起服务的日志行**；
3. **token 与 runtime**（按任务记，别只记聚合）。

**这次跑要回答的三个问题**：

| 编号 | 问题 | 为什么重要 |
|---|---|---|
| **A1** | 日志里**凭据是否被掩码**（有没有 key 的明文行） | 决定"平台容器里是否真的给了模型凭据"；影响我们能不能在平台侧做任何 LLM 调用 |
| **A2 · V-6** | **"非零"是按任务算还是按聚合算** | 决定"6 个都非零"这条闸门在榜单上怎么体现 |
| **A4** | 比赛模型的**真实规模与成本**（跑一次实际用了多少 token / 多少钱） | 决定 `pass/CNY` 能不能继续当排序口径 |

**红线提醒**：包里零题目特定字符串（`package.sh` 的闸门兜底）；**`.env` 绝不提交**；
**API key 不写进任何会被提交或被引用的文档**（本文件只写"去 `.env` 里拿"，不写值）。
