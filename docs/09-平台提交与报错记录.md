## 提交一：`probe-v1-doctor`（2026-09-20 14:5x）

### 报错原文

```
Run failed
Your run failed: web template is incomplete: expected frontend/ and backend/ directories
```

### 诊断：它检查的是"这次 run 留下了什么"，不是"zip 里有什么"

证据链（三条独立证据）：

1. 报错正文是 **"Your run failed"** —— 是**每次 run** 失败，不是上传校验失败。
2. ARC 自己的正常流程**第一步就是 `copy_template()`**（`app_type_handler/base.py:59-95`）：
   把 `web-react-express/`（里面正好是 `frontend/` + `backend/`）拷进 workspace。
   平台的这条检查与 ARC 的正常行为一致。
3. 我们的 `cmd_compile` 只做第 1 阶段：写事件 + traceability，**从不拷模板** →
   输出目录里没有 `frontend/`/`backend/` → 正好撞上这条闸。

### 这条闸为什么比我们以为的更靠前

`PLAN.md` §1 的判定链条第 1 环是"**跑得完**"——榜单要求同一份提交跑完全部 6 个任务。
**我们原先连"跑完"都做不到**，而原因不是生成质量，是**根本没产出应用骨架**。
`PLAN.md` §4.3 的"降级模式：保证产出可构建可运行的最小应用"说的正是这件事，只是我们此前低估了它的紧迫性。

### 修复：`pipeline/generate/scaffold.py`

- `scaffold_app(output_dir)`：把模板的**内容**拷进输出目录，让 `frontend/` + `backend/` 出现在**输出根**
- **模板查找优先级**：`ARC_AGENT_TEMPLATES_ROOT`（ARC 自己的变量）→ `ARCBENCH_TEMPLATE_DIR` → 包内 `templates/`
- **已有应用不覆盖**：输出目录里若已有 `frontend/` + `backend/` 就跳过并打印理由（兼顾决赛 evolution 语义）
- 找不到模板时**抛 `ScaffoldError` 并写 run-failed 事件**，不静默跳过
  （静默跳过正是这次踩坑的形态）

### 这次学到了什么

- 平台有**per-run 的结构闸**，而且它会给出**明确文字**——不要靠猜，读报错
- 骨架落地是"跑得完"的前置，不是优化项

## 提交二：`probe-v2-scaffold`（2026-09-20 15:2x）

### 报错原文

```
Run failed
2026/9/20 08:05:28
Your run failed: Runner exited with test failures or runtime errors
```

### 先别急着下结论：**这不是基础设施失败，恰恰相反**

同一跑的 Stdout 面板（2881 行，`/runs/2d5a2a44160f`）显示平台侧每一步都成功了：

```
Stage 2  Launching generation agent → Generation agent finished successfully
         generation-agent exit code: 0
Stage 3  Installing dependencies for frontend → Dependencies installed for frontend
         Building template frontend → Template frontend built          ← 平台自己构建
         Installing dependencies for backend → Dependencies installed for backend
         Starting template application server → started (pid=222)
         Template application is reachable on http://127.0.0.1:3000
         Preparing Playwright configuration → Using preinstalled Playwright package
         Deploying generated application → reachable on http://127.0.0.1:3000
         Deploying test environment → Test environment ready with 1 workers
         Executing tests with 1 workers → Test progress 0/86 …
         Playwright results parsed: passed=0, failed=86, score=0.0
         Runner exited with test failures or runtime errors
```

**真因：应用只有骨架、没有任何功能。** 每条测试的第一个交互（点击/查找某个元素）都找不到东西，
所以 86 条全挂。这是**预期结果**，而且它把"下一道闸"从基础设施问题变成了**生成阶段的工作**。

### 平台侧的事实（V5 的全部收获，全部有原文出处）

#### 1. runner 的 spec（原文）

```
[runner] Runner started with spec: {
  'agent_source': 'upload', 'runtime': 'python',
  'submission_dir': '/workspace/submission',
  'template_dir': '/workspace/template',
  'project_dir': '/workspace/template',
  'tests_dir': '/workspace/tests',
  'arc_dir': '.arc', 'requirement_dir': 'requirements',
  'output_dir': '/workspace/template',
  'runner_events_path': '.arc/runner-events.jsonl',
  'traceability_dir': '.arc/traceability',
  'task': {'category': 'web', 'requirement_id': 'arc-bench-web--prestashop',
           'test_runner': 'playwright'}
}
```

#### 2. 实际调用（原文）

```
[runner] Executing generation-agent: python3 /workspace/submission/main.py \
           /tmp/arcbench/requirements-source --output-dir /workspace/template
```

| 事实 | 值 | 对我们的意义 |
|---|---|---|
| 需求输入 | **位置参数**，值是**目录** `/tmp/arcbench/requirements-source` | `main.py` 必须接受"目录"形态（已支持） |
| 输出 | **`--output-dir`**（长选项），不是 `-o` | 我们的 argparse 两者都支持，且会把**参数来源**打进日志 |
| 输出目录 | **`/workspace/template`**（同时是 project_dir / template_dir） | 应用就写这儿；`ARCBENCH_*` 指向它下面的 `.arc/` |
| 注入的环境变量 | `MODEL` / `VISUAL_MODEL` / `ARCBENCH_RUNNER_EVENTS_PATH` / `ARCBENCH_TRACEABILITY_DIR` | 与 `.env` 同名 → "平台把 MODEL/VISUAL_MODEL 当环境变量注入"的推断**成立** |
| Python | **3.12**（`/usr/local/lib/python3.12`） | 本地 3.13；只要不用 3.13 专属特性即可（当前如此） |
| pip / npm | pip 走清华镜像；npm 走容器内配置 | — |

#### 3. 平台自带模板：`/opt/arcbench/templates/web-react-express`

我们 agent 打印的是：

```
模板已落地：/opt/arcbench/templates/web-react-express → /workspace/template（frontend/ + backend/ 齐备）
```

→ **平台自己带模板**，而我们的查找优先级（`ARC_AGENT_TEMPLATES_ROOT` → `ARCBENCH_TEMPLATE_DIR` → 包内 `templates/`）
**正确命中了平台那份**——比用我们包内那份更安全（平台模板必然与平台版本匹配）。

#### 4. 平台自己装依赖、构建、起服务

frontend `npm install`（**290 个包 / 16 秒**）→ `npm run build` → backend install → `npm run start` → 3000 端口可达。

→ **`frontend/dist/index.html` 由平台生成**（`docs/02` C2/C3 满足），
**我们不需要也不应该在 agent 里 npm install / build**（agent 跑起来之后没有网络）。
这条此前登记为"未决问题"，现已解决。

#### 5. 平台读到了我们的 traceability ✓

```
[runner] Initializing traceability store at /workspace/template/.arc/traceability
Stage 1: Traceability initialized with 109 requirements and 86 scenarios
```

109 节点 / 86 场景 = PrestaShop 的**精确值**。第 1 阶段的产物**被平台消费了** ✓
（走 SDK 高阶方法写的，符合"不得手工构造事件 payload"的要求。）

`/competition?competition=arc-bench-web` 实测 15 行，**没有 `suisui`**。分两级：
