## 一、六个赛题里有 2 个的需求文件不是合法 YAML 🔴

**这是今天最重要的发现。**

```
bookstack/requirements/requirements.yaml    第 603 行、第 645 行
keep/requirements/requirements.yaml         第 445 行

两个都是：ScannerError: mapping values are not allowed here
```

三处都是同一种毛病——**一个键比它的同级兄弟多缩进 4 格**：

```yaml
# bookstack:602-603        dash 在 14，键应在 16
              - keyword: GIVEN
                    content: The authenticated homepage shows ...   # 实际 20

# keep:444-445             同级键在 8
        type: ATOMIC
            description: 'Search notes by keyword and ...'          # 实际 12
```

### 为什么这条足以让榜单分不成立

1. 主赛道计分前提是**同一份提交跑完全部 6 个任务**（`PLAN.md §1`）。
2. 上游 ARC 的加载器就是裸 `yaml.safe_load`（`core/files.py:11-23`），**没有容错层**——它会在这两个文件上直接抛异常。
3. 也就是说，**"原样打包 ARC"这条保底路线，在这两个任务上拿不到分**。两条腿同时断 = 整条榜单分不成立。

9/19 实测该赛道 Current leader 仍是 `No data yet`，与此吻合。

### 我们的对策（已实现）

`pipeline/reqcompile/yamlrepair.py`：**解析器驱动的缩进修复**，只信 YAML 自己的判断：

1. 解析失败 → 取错误行号
2. 该行是 `key:` 形态 → 从"附近真实出现过的缩进值"里挑候选
3. 逐个试，**只接受让错误位置严格后退或让文件通过的那个改动**
4. 改不动就带诊断放弃，绝不产出半修好的树

实测结果：bookstack 修 2 处（均 20→16），keep 修 1 处（12→8），**两份都能解析了，节点数 56 / 45**。
每处修复都写进 `ValidationReport.repairs` 留痕——我们改了输入，赛后复核要说得清。

### ⚠️ 待验证

平台线上的需求包**是否也是坏的**。公开快照与线上包已知有差异（`PLAN.md` R2：ctrip 模块 125 vs 133）。
若线上是好的，这个修复器就是无害的冗余；若线上也是坏的，**它就是能不能出分的分水岭**。
→ V5 真实提交时用探针确认。

## 二、测试标题契约已 1:1 验证 ✅

`docs/02 §3` 记的规则是"`test()` 标题必须与 `scenarios[].name` 逐字、同序相等"。
今天把它验证到了**精确形式**：

> **测试标题 = `{req_id}: {scenario_name}`**

对 12306 做全量比对：

| | 条数 |
|---|---|
| 需求侧场景（按上述公式生成） | 135 |
| 测试侧实际 `test()` | 135 |
| **完全一致** | **135** |
| 只在需求侧 / 只在测试侧 | **0 / 0** |

### 这条为什么值钱

外部测试是**锁定且不可见**的——我们看不到它们，只能从需求倒推。
而上面的比对说明：**光凭需求文件就能 100% 还原测试清单**（标题集合，以及标题顺序）。

直接后果：

1. **生成阶段的靶子不需要猜。** 需求里有多少场景，就会有多少条外部测试，标题逐字已知。
2. **其余 5 个没有参考实现的 app，也能预先算出测试清单。** 这对排期（`PLAN.md §7` 的墙钟外推）和覆盖率对账都是直接可用的输入。
3. **`scenarios[].name` 是不可改写的。** 不能翻译、不能加前缀、不能"优化措辞"——改一个字就挂不上。

## 三、可访问名契约的表述**不统一**（修正 PLAN.md §4.1）⚠️

`PLAN.md §4.1` 说"已知需求文档会显式写这条要求"，引的是 **quickstart 示例**的中文原文：

> 必须提供以下稳定且唯一的中文可访问名称，供 Playwright 使用 `getByLabel` 或 `getByRole` 定位……

**实测：六个赛题里都不长这样。** 关键字出现次数：

| app | `accessible name` | `labeled` | 汉字数 | 主要句式 |
|---|---|---|---|---|
| 12306 | 0 | 13 | 0 | `input fields labeled "Name", "Passport number", …`、`the "Register" button` |
| bookstack | 0 | 0 | 0 | `"Email address" field`、反引号 `` `New Shelf` `` 表示可点击 |
| ctrip | 0 | 2 | **989** | 中英混排 |
| keep | 0 | 2 | 0 | 英文 |
| prestashop | 0 | 0 | 0 | `Click "Sign in" link`、`"Clear all" button` |
| stackoverflow | 0 | 0 | 0 | `"Log in" submit button`、`"Forgot password?" link` |

- **`accessible name` 这个词一次都没出现。**
- 只有 **ctrip 带中文**；其余五个是纯英文。
- 12306 的主流写法是 `input fields labeled "Name", "Passport number", ...` 与 `the "Register" button`。
- bookstack / prestashop / stackoverflow **连 `labeled` 都不用**，句式各不相同。

**推论：不能为某一种句式写死抽取器。**

### 已实现：模式表驱动的抽取器（`pipeline/reqcompile/a11y.py`）

不猜一种句式，而是**把观察到的每种句式各写成一条规则**；新增 app 只加规则、不动代码。
四条规则（去重后）：

| 规则 | 形态 | 例子 |
|---|---|---|
| A 中文契约 | `` `X` 为[必填/可选]…输入框 `` | quickstart / ctrip |
| B `labeled` 锚点 | `labeled "A", "B", "C"` | 12306 的表单字段 |
| C 角色词在前 | `the tabs "Popular", "ABCDE", …` | 12306 / stackoverflow |
| D 兜底 | 引号名字 + 邻近角色词 / 点击动词 | bookstack 的反引号点击 |

**实测覆盖率（12306，有真实测试做地面真值）：98%。**

- 抽取 441 条 / 124 个去重名
- 测试实际用到 57 个名字，覆盖 56 个
- 口径是**子串匹配**——因为 Playwright 的 `getByRole({name})` / `getByLabel`
  默认就是大小写不敏感的子串匹配，所以"我们抽到的名字与测试用的名字互为子串"
  才算真正可用（精确匹配口径只有 74%，会低估）

唯一没覆盖的 1 个是
`you can make travel plans through the ticket reservation function.`——
它在需求里是**裸可见文本**（没有引号、没有 label），任何基于引号的抽取器都拿不到。
这类"测试直接点可见文本"的名字只能靠实现阶段把需求里的文案原样渲染。

**落地过程中踩到的两个真 bug（都值得记住）：**

1. `\btab\bs?` 这种写法让**复数永远匹配不上**（`\b` 要求 tab 后先有词边界，
   而 "tabs" 后面紧跟的是 s）。`tabs` / `buttons` / `fields` / `options`
   这些复数锚点整批失效，是覆盖率卡在 70% 的主因。正确写法 `\btabs?\b`。
2. 中文契约句**不能按 `；` 切句再要求每句以反引号开头**——引言（"必须提供
   以下稳定且唯一的中文可访问名称……："）和第一个名字在同一句里，
   那样会漏掉 `用户名`。改成在整段里直接搜索模式。

**回归验证**：`python eval/check_reqcompile.py`（全绿才继续）。

### 三补 · 六 app 召回抽检已做（2026-09-20）——抽取器的有效范围是「引号式」需求 ⚠️

`PLAN.md §4.1` 要求"对每个 app 抽检召回率，且在批量生成之前做"。**这一条已完成。**

- 探针：`docs/06-a11y-recall-probe.py`（测量脚本，非提交物）
- 完整输出存档：`runs/20260920T-a11y-recall-all-apps.txt`（93 行，含每个 app 的未覆盖清单与 0 名单元号）
- 复现：`python docs/06-a11y-recall-probe.py`

**方法（与检查 3 同口径，只把"测试用名"的抽取换成通用规则）**

1. 地面真值 = 测试文件里实际用于定位的名字：**引号字面量** + **正则字面量**（`/logo/i` → 归一化还原成 `logo`；这些 app 的测试大量用正则，只用引号会误判为"测试不用名字"）
2. 名字位置参数**自动识别**，不写死：解析各 app 的 `helpers.ts`，判据是"该形参被 `toPattern(p)` / `resolveNamed(scope,p)` / `resolveField(scope,p)` 使用"，并做 `for (const v of p)` 与跨 helper 传递的不动点迭代。实测：12306 识别出 **13/59** 个名字位置 helper
3. 命中 = 子串双向匹配、大小写不敏感（Playwright `getByRole({name})` 的默认语义）
4. **模块级空转率** = 有场景的叶子里"一个可访问名都抽不到"的比例。名字被归到祖先节点的只有 0–3 个/ app，影响可忽略

**结果**

| app | 生成单元 | 0 名单元 | 空转率 | 引号名条数 | 条数/单元 | 测试用名 | 命中 | 召回 | 召回下界 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 12306 | 117 | 6 | **5%** | 441 | 3.8 | 177 | 141 | 80% | 81% |
| bookstack | 34 | 8 | 24% | 54 | 1.6 | 30 | 28 | 93% | 97% |
| ctrip | 125 | 32 | **26%** | 132 | 1.1 | 117 | 41 | 35% | 44% |
| keep | 32 | 16 | **50%** | 33 | 1.0 | 30 | 20 | 67% | 74% |
| stackoverflow | 66 | 29 | **44%** | 67 | 1.0 | 46 | 32 | 70% | 76% |
| prestashop | 86 | **53** | **62%** | 39 | 0.45 | 89 | 35 | 39% | 45% |

- **召回下界**：把"未命中且需求文本里出现过该字符串"的项**全部**当作真缺口算出的保守下界（该判定用子串，偏松，所以这是下界不是估值）
- 0 名单元清单在存档里（例：prestashop 53 个、keep 16 个、stackoverflow 29 个）

**诊断：差异是「种类」，不是「程度」**（抽查验过，不是推断）

- **引号式**（12306）：`input fields labeled "Name", "Passport number"`、`the result count "0 results"` —— 名字在引号里，抽取器原理上吃得到
- **散文式**（prestashop / stackoverflow / ctrip / keep）：
  `THEN: Display Logo, category menu, search box, language selector, user entry, cart icon`
  ——**零引号**，而对应测试写的是 `/logo/i`、`/search/i`、`/cart/i` 这类大小写不敏感正则
- 抽取器的入口是 `_iter_quoted()`（`a11y.py:219`）——**按构造就是引号驱动的**，散文名词在结构上抽不到

### 三补-2 · 验收口径已收窄为「交互单元空转率」（2026-09-20，按第五轮审核 + `PLAN.md` §4.1 裁定）

**为什么收窄**：上表的"0 名单元率"把**纯散文、无点击/输入的单元**也算进了分母——
那些单元本来就不该有可访问名，混在里面会让"空转率下降"变成假信号。

**交互单元** = 场景名或任一步骤里含 `click / select / enter / check / submit` 的单元。
输出存档：`runs/20260920T-interaction-unit-a11y.txt`（旧口径存档 `runs/20260920T-a11y-recall-all-apps.txt` 保留不动，它已被第三/第四/五轮审核引用过）。

| app | 生成单元 | 交互单元 | 全部单元空转率 | **交互单元空转率** |
|---|---:|---:|---:|---:|
| 12306 | 117 | 99 | 5% | **2%** |
| bookstack | 34 | 32 | 24% | **19%** |
| ctrip | 125 | 112 | 26% | **18%** |
| stackoverflow | 66 | 49 | 44% | **29%** |
| keep | 32 | 25 | 50% | **40%** |
| prestashop | 86 | 66 | 62% | **50%** |

**排序不变**（12306 最好、prestashop 最差），但**量级全线下移**，其中 ctrip 从 26% → 18%、
bookstack 24% → 19%。**这两列必须都报**：只用收窄后的口径会低估问题的广度，
只用收窄前的会高估严重度。

> 🔁 **踩到与 §三 同一个坑（值得单独记）**：第一版判据写的是 `\b(?:click|select|…)\b`，
> 结果 bookstack 只识别出 6/34 个交互单元、算出 **83%** 的空转率（比不收窄还差）。
> 原因是 bookstack 的需求文本写的是 **`clicks the "Save" button`（第三人称单数）**。
> 加词形后缀（`s|es|ed|d|ing|ted|ting`）后变成 32/34 个交互单元、19%。
> **这与 §三 记过的 `\btab\bs?` 是同一个坑：需求文本的动词/名词带后缀，锚点写死就整批失效。**
> 凡写模式表，先拿一个 app 的数字做常识核对（"34 个单元里只有 6 个要交互"本身就可疑）。

**与本节前面「12306 98%」的关系：不矛盾，口径不同。**
98% 的分母是 57 个名字（只统计经 6 个 helper、且以 `page` 为 scope 的调用）；
上表 80% 的分母是 177 个（13 个名字位置 helper + `getByPlaceholder/Text/Title/hasText` + 正则字面量）。
两个数都对，但**只有后者能回答"闸门覆盖面"**。

**对方案的含义（⚠️ 属"闸门设计"改动，待检查点裁定，此处只登记事实与建议）**

1. §4.2 的 L1 闸门按"需求声明的可访问名都存在"设计——**它只对 12306 有效**。
   对 prestashop / keep / stackoverflow / ctrip，多数生成单元它**无事可查**
   （交互单元空转 50% / 40% / 29% / 18%；全部单元口径 62% / 50% / 44% / 26%），
   表现为"闸门报绿但外部测试大面积失败"——这正是 §4.1 担心的形态，现在有数了。
2. 要补的不是"一两条句式"，而是**第 5 条规则：散文名词枚举**（`Display X, Y, Z` / `Click the X link` /
   `shows the X`），把**无引号**名词短语提成清单；同时 L1 判据要按 app 分两类：
   - 引号式 → 查精确名是否存在
   - 散文式 → 查"该名词是否出现在某个元素的可见文本 / 可访问名里"
3. **排期**：`PLAN.md §4.1` 已写明它"应该在批量生成之前做"，所以它是 **M4 阶段的前置**，不是可选项。
   成本量级：一张模式表 + 一次按 app 的召回抽检重跑（本探针可直接复用）。

## 五、复现方式

```bash
from reqcompile import load_requirement_tree, build_scenario_index

base = pathlib.Path('../repos/arc-bench/arc-bench/webapp')
for app in ['12306','bookstack','ctrip','keep','prestashop','stackoverflow']:
    tree, rep = load_requirement_tree(base/app/'requirements'/'requirements.yaml')

          'errors', len(rep.errors), 'warnings', len(rep.warnings))
"
```
