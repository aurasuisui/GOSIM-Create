## 二、🔴 `check_db_tables` 的 bug 我定位到了：**类型不匹配**（不是判据宽严）

我拿盘上现存的 5 个产物直接跑了这个函数（`%TEMP%` 下都还在）：

```python
sys.path.insert(0,'pipeline'); from verify.l1 import check_db_tables
# m3b0            findings=4    ← 它建了 users/sessions（auth_repository.js:22/37）
# m3b1-low        findings=4    ← 它也建了（auth_repository.js:43/68）
# m3b1-flashdef   findings=4
# m3b1-gate0b     findings=4
# m3b1-glm        findings=4
```

**五个产物给出完全相同的 4 条**（`sessions` / `test_harness` / `tests` / `users`）。
根因是把两个集合相减时**左边是元组、右边是字符串**：

```python
used |= {(m.group(1).lower(), rel) for m in re_from.finditer(text)}   # (表名, 文件)
created |= {m.group(1).lower() for m in re_create.finditer(text)}     # 只有表名
...
for table, rel in sorted(used - created):    # ← 元组集合 − 名字集合 = 永远不消掉任何元素
```

实测三行（`m3b0`）：

```
created = ['sessions', 'to', 'users']                    ← 正则本身是好的
used    = [('sessions',…auth_repository.js), ('test_harness',…seed_db.js),
           ('tests',…seed_db.js), ('users',…auth_repository.js)]
used - created                    = 上面 4 条全在   ← 现实现
{名字} − created                  = ['test_harness','tests']  ← 应有结果
```

→ **正则没错，错的是集合运算**——这正好解释你们那句"同样的正则单独跑是对的，in-function 路径上我没定位到原因"。

**一处修**：`missing = sorted((t, r) for t, r in used if t not in created)`

**还有第二处（token 卫生）**：`test_harness` / `tests` 来自 **JSDoc 注释**——
`backend/src/database/seed_db.js:15-16`：

```
15:  * 3. Reuse this entrypoint from tests and dev scripts …
16:  * 4. If a test needs DB state, … from `test_harness.js`,
```

`FROM tests` / `` FROM `test_harness `` 被当成 SQL 了。→ **匹配前先剥掉 `//` 与 `/* */`。**
不剥的代价不只是噪声：**每条假发现都会换来一轮定向修复（= 一次全量重发）**，
而你们刚测出"闭环自己占 65% token"。

**修好后的预期行为（可直接当回归夹具，5 个产物还在盘上）**：

| 产物 | 应有 findings |
|---|---|
| `m3b0`（deepseek-chat, 6/6） | **0**（它建了表） |
| `m3b1-low`（flash+low, 5/6） | **0** |
| `m3b1-flashdef` / `m3b1-gate0b`（flash 默认, 3/6） | **含 `users`、`sessions`** |

## 五、🟡 补一条理由：**"让模型改对地方"这条路径不可靠**（支持"schema 由管线落位"）

`§九.1` 给了两个选项，我建议直接选第二个（管线落位），理由是模板里那个插入点很脆：

- `init_db.js` 的引导注释在 `initializeDatabase()` 的 IIFE 里，**而 `return database;` 是我们为修上游 bug 加的那一行，位置就在注释之后、`})();` 之前**；
- 模型改代码的习惯是**追加到块的末尾** → 很容易落到 `return database;` **之后**，成为**永不执行的死代码**，
  表现与"完全没建表"一模一样。

→ **管线落位**（模型单独产出一段 schema，由管线注入到 `return database;` **之前**并确保启动时执行）
把这件事从"模型改对位置"变成"结构上不可能漏"。
