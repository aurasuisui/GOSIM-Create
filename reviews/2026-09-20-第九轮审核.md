## 四、建议补进表里的两项（都便宜，且我们自己就能答）

### 4.1 「非零」的**判定口径**——决定 M3b 的目标怎么写

我们手上这一跑是"6 个任务各 0.0% → 不在榜"，它**无法区分**两种读法：

- (a) **按任务**要求非零：每个任务都要有 ≥1 条通过；
- (b) **按聚合**要求非零：允许个别任务 0 分，只要平均分 > 0。

两者的工作量差很多（(a) 要求每个 app 都铺开，(b) 允许先集中做一个）。
**验法**：用同一份快照，只在一个任务上做到部分通过（比如 keep，32 条里过 3–5 条）再跑一次，
看①该 run 是否被标为 completed（而不是像 0/86 那样 failed）；②榜单是否出现条目。
**顺便回答 `docs/08:100` 已有的那个问题**——同一快照能否反复跑任务（决定 M3b 的操作模型：
能否在同一快照上多轮迭代而不重新上传）。

### 4.2 V-4 的验法可以更锐利（用我们自己的 run 页做对照）

`PLAN.md:50` 的验法写的是"bbs 提问 + 用自己提交的 token 读数与 meter 对账"。可以加一条**当天就能做的**：

> **可证伪预测**：我们自己的 run 页面（stage 1 + 拷模板，**零 LLM 调用**）应当显示
> `Runtime ≈ 0–2s`、`token 0.00M`。若属实，而榜单前几名同样是 `0s / 0.00M`，
> 则 `Runtime` 量的是 **agent 阶段**而不是整跑墙钟——那 0-token 高通过率条目就是
> "agent 没做生成工作"，R10 的两种可能里偏向"预埋/不计量的路径"。
> 这一步不需要提问，看自己的 run 页即可。

（`docs/09` 已记 `Download code` 可下载产物——**只用于理解计量口径，不要照抄任何别人的产物**，
那会撞"不得预埋答案"的红线。）
