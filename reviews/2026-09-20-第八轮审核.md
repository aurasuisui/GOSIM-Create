## 三、本轮新增的三条建议

### 3.1 🔴 最高 ROI：把"跑官方测试"接到**我们自己生成的应用**上（本地闭环）

现在的本地测量只能打 12306 **参考实现**（`docs/04:368`、`PLAN.md:816` 都是 `--target-url 127.0.0.1:3301` 指向它）。
但 `arc-bench` 里 **6 个 app 的测试文件都在**，runner 也支持任意 `--app` + `--target-url`。于是 M3 的全部迭代可以这样做：

```bash
# 生成 → 起我们自己的应用 → 用官方测试打它（不花平台 token、不需要用户上传）
python pipeline/main.py <需求目录> --output-dir /tmp/appX
cd /tmp/appX/backend && npm run start &            # 或按契约起在指定端口
cd repos/arc-bench && npm run test -- --app prestashop --target-url http://127.0.0.1:<port>
```

**为什么这条最重要**：平台的每次"跑任务"要**用户手动上传 + 逐任务点选**，而 M3 的目标是
"6 个任务全部非零通过" —— 那必然是一个**多轮迭代**，靠平台跑迭代等于把用户变成瓶颈。
本地跑外部测试不消耗平台额度、不占用 bench 锁以外的资源、还能吃到 `extract_run.py` 的 per-test 归因。

**建议**：把 `eval/bench.sh` 的目标从"参考实现"推广成"任意 backend 目录 + 任意 app"
（或加一个 `eval/bench-app.sh`），并登记为 M3 的第一件事。
⚠️ 口径差异已知：本地套件 478 条 vs 平台 484（12306 +3），约 1.2% 代理差异，只做相对判断。

### 3.2 🟡 榜单 `Runtime` 列大概率**不是**整跑墙钟——它对 M3 的"墙钟 × 6 外推"是错的口径

- 事实：`#2 你也秃对不队` 82.1% / 0.01M token / **2s**；`#5 jackyjiang` 100% / 0.00M / **0s**；`#6 FT-踏歌行` 83.6% / 0.00M / **7s**；
  而 `#3 JustSoSO` 62m、`#4 chrislearn` 379m。
- 2 秒不可能完成"装 290 个 npm 包 + build + 起服务 + 跑 86 条 Playwright"（我们那轮的平台侧步骤本身就远超 2s）。
- **自洽的假设**：`Runtime` = **agent（生成）阶段**耗时，`Total Token` = agent 消耗的 token。
  于是 0–7s 那些条目 = "agent 几乎没做生成工作"，与 `0.00M` 并列完全自洽。
- **可证伪的预测**：**我们自己的 run 页面上，Runtime 应当是 ~0–2s、token 0.00M**（第 1 阶段纯代码、零 LLM 调用）。
  让用户在自己的 run 页看一眼就能确认/否证——这是零成本的判定。
- **两个后果**：① `M3` 的"墙钟 × 6 外推与平台上限比对"**不能用这个列**，要自己计时（平台 Stdout 有时间戳，本地也有）；
  ② 若假设成立，"0 token 拿 80–100%"意味着那些提交**没有现场生成**——要么预埋、要么走了不计量的路径，
  `PLAN §1` 的"唯一变量是 token"就仍然不安全，**M4 降本应继续冻结**直到搞清。
  （`docs/09:182` 已把它标为"待解现象，不要据此下结论"，这个克制是对的；上述假设只是给它一个更锐利的形态。）
- 可选的调查手段：run 页有 `Download code`，看**一个 0-token 高通过率条目**的产物是"真生成"还是"预埋"即可定性
  —— 只用于理解计量口径，**不要照抄任何别人的产物**（那就撞二次审查红线了）。

### 3.3 🟡 `PLAN.md §2` 仍留在旧保底框架，与 §M2 冲突

- `§2` 仍写"**保底包必须是「ARC + 输入修复壳」**……确保榜上有名"（`PLAN.md:41-56` 一带）；

- `§2` 是"路线决策"节，读者会把它当结论。建议在 §2 那段加一句
  "⚠️ 该框架已被 M2 的实际结果取代：跑通平台的是自研管线，见 §M2"，而不是让两节各说一套。

## 四、战术建议：M2/M3 的第一步该挑"只要导航就能过"的场景

"6 个任务全部非零"的**最便宜路径**不是实现功能，而是先把
**只有导航、不需要业务逻辑的场景**做出来并确保可访问名对得上：

- 例（12306 夹具风格）：`Open the login page from the "Login" link in the top-right area`
  —— 只需要一个 accessible name 命中 `Login` 的可点击元素 + 一次跳转。
- 这类场景在 6 个 app 里都有一批（`docs/06` 的场景清单 + `a11y` 抽出的靶子清单可直接筛）。
- 收益：把"不在榜"变成"Junior 榜上有名"（**上分靠的就是非零**），成本是**最小量的功能**而非完整实现。
- ⚠️ 前提：先确认平台对"非零"的判定口径（`3.2` 的实验顺带回答：**部分通过（比如 30%）的 run 是否被标为 completed**）。
