## 3. 🔴 真实关键路径（与 PLAN 的写法不同 —— 这是重订计划最要紧的一点）

PLAN 的写法是"**闸门第 0 条 → M3b-1 铺开**"。**实际上**：

- **闸门第 0 条用的是 `quickstart`，而它不是主赛道任务**（主赛道是 12306/bookstack/ctrip/keep/prestashop/stackoverflow）。
  → **即使 gate 0 拿到零人工 6/6，M2 依然是 0**（排行榜只认主赛道任务）。
- **M2 要的是"某个主赛道 app 非零"**，那就必须：**通用分块器**（现在的 `CHUNKS` 与各块 `ask` 是注册专用的，
  拿它跑 keep 只会产出注册应用 → 必然 0/32）→ 在 `keep`（32 条，最小，yamlrepair 已能解析）上本地跑到非零
  → 打包 → 你跑一次平台。
- **通用分块器同时服务 M2 与 M3b-1**，而 gate 0 的第六次跑只服务"验证规则"——
  而三条规则里两条已经是**静态可判**（`syntax_balance` 已在 L1；`<meter>` 缺 ARIA 名也可以做成 L1 检查）。

**结论：关键路径 = 通用分块器 → keep 本地非零 → 打包 → 平台跑一次（同时答 A1/A2）。**
第六次 quickstart 跑**不是必需项**。

   验证方式只需一行日志（掩码 key 存在性）。
3. **"零人工"作为唯一读数口径**：手工补过的一律标注、**不进闸门判据**。

   把"必须重新生成才能验证"的东西压到最少——今天 97 万 token 的教训就是"用生成去验静态规则"。
5. **每个 app 的 token 上限 + 到额降级**（配额未知下的硬要求）。
6. **保留"历史产物当回归语料"**（`%TEMP%` 下已有 6+ 份产物）：M3b-1 会不断加检查，
   有了矩阵才能一眼看出新检查是"又宽又松"还是"又紧又假"。
