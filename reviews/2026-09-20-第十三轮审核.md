## 二、🔴 C 组（`glm-5.3-flash`）的 0/6：**根因写错了**，真实形态是"应用在跑判据中途死了"

`docs/12 §三` 写 C 的原因是"**用户名渲染成拼接文本** → `getByText(username, {exact:true})` 匹配不到"。
但我去数了那 6 条失败：

```bash
grep -E "Error:" runs/20260920T-m3b1-glm-flash-0of6.log | sort | uniq -c | sort -rn
#   5  Error: page.goto: net::ERR_CONNECTION_REFUSED at http://127.0.0.1:3301/
#   1  Error: expect(locator).toBeVisible() failed   ← 这一条才是用户名拼接（第 52 行）
```

**6 条里 5 条是"应用在 3301 上不可达"**。而失败顺序给出了更准的形态：

- **第 1 条**（`REQ-1: successfully register…`，spec 第 48 行）**真的跑起来了**——页面加载成功、
  走到注册后的断言才失败（第 52 行）→ **说明应用当时是活的**；
- **第 2–6 条**（都是 spec 第 72/84/96/104/120 行的拒绝路径）**全部 `ERR_CONNECTION_REFUSED`**
  → **应用在第一条测试之后就不在了**。

→ 正确的读法是：**`glm-5.3-flash` 的产物存在"注册流程触发后端崩溃"这类缺陷**，
而"用户名拼接"只解释了 1/6。你们已经记下的那条教训（`docs/12 §六`：*跑判据前必须先确认探活 200；
等待循环超时了就该停下来，不能继续*）在这里同样适用——**这次记录的是"崩溃"，不是"没功能"。**

**这条直接推出一条闭环能力缺口**：
`pipeline/verify` 的 L1 是**静态**的（`docs/11 §六.2` 自己写了"抓不到语义"），
自检是**模型判断**的；两者都**不会把应用真的起起来打一下**。
所以"应用一起来就崩"这类缺陷在闭环里是盲区——而它在平台上等于大面积失败。

**建议（M3b-1 之前）**：闭环里加一步**冒烟**：起服务 → 打一次入口路由 → 确认 HTTP 200；
有 spec 的场景标题时，连"第一个断言"也跑一下。它同时是你们 M3b-1 第一条
（"每个 app 都能在本地用官方测试打分"）的自然组成部分——**本地跑官方测试就是最强的冒烟**。

## 三、🔴 B 组的成本数字**少算了一次调用**，而且和你们自己的口径声明矛盾

`docs/12 §三` 写：B = `8 calls / 81,862`。但记录文件是 **9 条 / 120,326**：

```
# runs/20260920T-m3b1-flash-low-metrics.jsonl（连续一次运行，无 >3 分钟空档）
 1 12:03:20 design        2,981      6 12:05:06 selfcheck-review      19,407
 2 12:03:56 backend-auth 14,798      7 12:05:24 repair-RegisterPage  11,432
 3 12:04:10 backend-routes 12,010    8 12:05:25 repair-HomePage       1,029
 4 12:04:31 frontend-reg  12,381     9 12:07:11 selfcheck-review     38,464
 5 12:04:40 frontend-shell 7,824     ─────────────────────────────────────
                                     合计 120,326
```

**差额 38,464 = 恰好是第 9 条**（那一次 selfcheck-review）。于是：

| 配置 | 文档写的 | **记录文件实际** | 文档的 token/通过 | **实际 token/通过** |
|---|---:|---:|---:|---:|
| A `deepseek-chat` | 92,158 / 6 | 92,158 / 6 ✓ | 15,359 | 15,359 |
| **B `flash + low`** | **81,862 / 5** | **120,326 / 5** | 16,372 | **24,065** |
| C `glm-5.3-flash` | 53,723 / 0（判据待重测，见 §二） | 53,723 / 0 | ∞ | ∞ |

→ **结论方向不变（A 仍最优），但差距从 7% 变成 57%**；
而 `docs/12 §五.3` 自己写着"用本次三行的 token（**含全部尝试**）当基线"——
**表里恰恰漏掉了一次调用**。判定"B 更贵"这件事因此变成"B 明显更贵"。

**根因不是手滑，是工具**：`metrics.jsonl` 的记录**没有 `run_id`**，
所以"这一次 run 花了多少"只能靠人工在时间线上挑。同样的错误在 `docs/10 §6` 已经发生过一次
（`5 次 / 89,948` vs 记录 `6 条 / 103,847`，差 13,899 = 两次 design），**两轮未修**。

**建议**：① 给 metrics 记录加 **`run_id`**（或每次 run 一个独立文件）；
② 用它**重建 `docs/10` 与 `docs/12` 的两张成本表**，并按 `PLAN §4.4` 的规则给两栏
（成功路径 / 含全部尝试）；③ 把"表格必须由脚本从记录聚合，不许手抄"写进 `docs/04` 的记录纪律。

## 四、🟡 三条要补的前置（都会影响 M3b-1 能不能跑起来）

### 4.1 平台容器里"能不能调到模型、拿什么凭据"——**至今未验证**

- `docs/09 §1` 记的平台注入变量是 `MODEL` / `VISUAL_MODEL` / `ARCBENCH_RUNNER_EVENTS_PATH` /
  `ARCBENCH_TRACEABILITY_DIR`——**没有 API key**。
- 而此前三次提交（probe-v1 / probe-v2 / doctor）**全是零 LLM 调用**，所以这条从未被触发过。
- `pipeline/generate/llm.py` 的回退链是对的（`PIPELINE_LLM_*` → `OPENAI_API_KEY`/`ARC_API_KEY`/
  `ARC_OPENAI_API_KEY` → 工作区 `.env` 兜底，base/model 同理）✅ ——但如果**平台一个 key 都不注入**
  而网关又需要 key，M3b-1 在平台上会**直接失败在第一次生成调用**。
- **廉价解法**：在 agent 启动日志里加一行**掩码的存在性检查**，例如
  `key: OPENAI_API_KEY=set(len=56) / ARC_API_KEY=absent / base_url=… / model=…`。
  下一次提交（哪怕还是零调用）就能定论。**这条应列进 M3b-1 的闸门**，别等到铺开时才发现。

### 4.2 本地迭代模型 ≠ 平台模型 → 需要一条**固定的"提交前最后一步"**

标定刚证明：**换个模型能把 6/6 变成 0/6**（A vs C）。而 `docs/12 §五.1` 的决定是
"本地迭代用 `deepseek-chat`（官方档），平台提交时用网关的 `deepseek-v4-flash`"。
这两件事放在一起，正好构成"本地 6/6 → 平台 0/6"的经典组合。

`§五.4` 已经排了"同一网关上补一次 `deepseek-v4-flash`（默认）端到端"——**建议把它升格为纪律**：
**每次提交前，在平台模型（网关的 `deepseek-v4-flash`、不加 `reasoning_effort`）上跑一次确认。**
本地便宜迭代 + 平台模型确认，两件事都要，不能只留前者。
