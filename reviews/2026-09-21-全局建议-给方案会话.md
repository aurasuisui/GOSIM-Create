## 3. 一个必须算出来的数：六 app 的判分墙钟

keep 的实测是 **32 条 = 30.7 分钟**，而它是**失败主导**的：31 条失败各耗约 **60 秒**（等待/超时），
通过的那条只花 **431ms** / **339ms**。→ **每条失败 ≈ 59 秒。**

按这个真数外推（假设失败为主）：

| app | 判据数 | 最坏墙钟 |
|---|---:|---:|
| 12306 | 135 | ≈ 2.2 h |
| ctrip | 126 | ≈ 2.1 h |
| prestashop | 86 | ≈ 1.4 h |
| stackoverflow | 67 | ≈ 1.1 h |
| bookstack | 34 | ≈ 34 min |
| keep | 32 | ≈ 31 min |
| **合计** | **478** | **≈ 7.4 小时** |

**两个推论，都要写进排期：**

1. **"跑得完"和"非零"不是两个独立风险，是同一个。** 通过率上升会显著压缩墙钟（失败在烧超时）。
   → 提高通过率**同时**降低"跑不完"的风险。这条反过来说也成立：**大面积失败的一条提交，可能自己把自己拖死。**
2. `PLAN.md` §4.3 现在用的外推锚点是"12306 单 app 3.6–8 分钟"——
   **那是参考实现全通过时的数字**，与"大面积失败"的形态差一个数量级。
   要用 **7.4 小时**这个数去问 A3（墙钟上限）。

## 5. 三条应当被纠正的说法（防止下一轮继续被引用）

```bash
cd repos/arc-bench/arc-bench/webapp/keep
```

## 6. 明确不建议做的事（附理由）

| 不建议 | 理由 |
|---|---|
| **推翻架构重写** | §1.1 那五项已证资产**会全部丢掉**，而它们恰好是"已经跑在正确位置上"的部分。9 天里重写要花 2–3 天回到同等位置。**不满的是推进速度，不是架构质量** |
| **换 ARC 主线** | `arc compile` **一次都没跑过**；它的结构性 token 劣势（严格串行 DFS / 每叶子 3 场会话 / TDD 最多 15 往返）正是当初放弃它的理由。换过去 = 付重写成本 + 拿更差的经济性 |
| **换通用 coding agent 做基座** | 五个候选（opencode / codex / pi / DSH / ZCode）我逐个核过：**没有一个是 diff-only 协议，全部每轮重发整个对话**；我们的任务形状是 460 个原子单元、无人值守、有硬预算，而它们是"人在回路 + 单个仓库 + 一个人类尺度的任务"。等于在 `pass/CNY` 分母上乘常数。**值得偷的是设计不是代码**：patch 协议、上下文预算（pi 的 reserve/keep 双阈值 + 迭代摘要）、只读子代理 + 便宜档路由、从持久日志推上下文压力 |
| **现在建视觉通路** | 见 C1：动机例已证伪，先做便宜的链路排查 |
| **追 100% 通过率** | 满分**可达但不稳定**（实测区间 129–135，五轮一次满分）。理由从"满分不存在"改成"满分不稳定"，但结论不变 |

   模型 review 只保留在本地判据覆盖不到的地方——而"代码形状"这类**已经由 L1 十条管住了**，
   所以 review 的剩余价值本来就很小（这正是它占 50.3% 却量不出收益的原因）。

**能用零 token 判的不要用生成去验；能在本地验的不要留给平台上的自愈。**

## Q20 · 有区分测试，而且它就是 R1 的副产品（**这条让 R1 的价值又高一档**）

**能分辨**，因为我们**自己记了每次调用的 token**（`.arc/metrics.jsonl` + `eval/aggregate_metrics.py`），
而平台会报它自己计到的 `Token`。所以对账方法是一行话：

> **拿同一次 run 的两个数比：我们自己的合计 vs 平台榜单那一行的 `Token`。**

三种结果、三种结论：

| 观测 | 结论 | 动作 |
|---|---|---|
| **平台 ≈ 我们的** | 计量口径正确 → 前几名 `0 token / 80–100%` 是**异常** | 按 Q17.b 问主办方（**规则/公平性问题**，不该由我们猜） |
| **平台 ≈ 0，而我们是几百万** | **计量只统计走平台网关的那部分** | R10 结案；`pass/CNY` 的优化方向要重估（**M4 的整个前提**） |
| 平台计到某个中间值 | 又是一条新口径（例如只算 agent 阶段） | 记下来，作为新基线 |

**第二种是最可能的，而且它可解释**：`pipeline/generate/llm.py` 有 `PIPELINE_LLM_*` 回退链，
**我们本地迭代时就在用 DeepSeek 官方档**。若某队把 agent 指向自己的 key/额度，
平台网关就看不到 token——**而这不违反"必须用发放的 token"以外的东西**（那条是规则问题，正好也是 Q17.b）。

**→ 所以 R1 一次答三件事：A1 + A2/V-6 + R10/V-4。这是把它排在最前的又一个理由。**

**一条 op 前提**：要把对账做成可判，R1 之前必须**把这次 run 的 `metrics.jsonl` 单独存一份并记进 RunRecord**
（顺手补掉 `model: unknown` 那个记录缺口），否则事后无法归属、对账做不成。
