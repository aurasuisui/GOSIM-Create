## 二、我独立复核过的三件（都成立）

### 2.1 ✅ 上游模板 bug 是真的，补丁落点也对

`docs/10 §5.2` 说"模板副本与上游逐字节相同"，我直接去只读仓库验了机制，**成立且定位准确**：

```js
// repos/arc-template/templates/web-react-express/backend/src/database/init_db.js
if (initPromise) { return initPromise; }      // ← 第二次调用走这里
const database = getDb();
initPromise = (async () => { await runStatement(database, 'PRAGMA foreign_keys = ON;'); /* … */ })();
                                              // ← 这个 IIFE 没有 return → 解析成 undefined
return database;                              // ← 只有第一次调用能到这里
```

而 `database/db_runtime.js` 的 `run/get/all/exec/withTransaction` **全部**是
`const database = await initializeDatabase();` 再当句柄用 → **第二次起必然 TypeError**。
我们包内副本的差异**只有一行**（`diff` → `78a79 > return database;`），且落在 IIFE 内部（`})();` 之前）✅ 正确。

**结论的分量比文档写的还重**：这是**平台自带模板自己带的 bug**，用它的队伍都会踩到；
而 `apply_known_fixes()` 打在**产物**上（不是只改自己副本）——我读了实现，**幂等 + 模式保护**
（`fix["fixed"] in text` 先跳过；`fix["buggy"]` 不命中就 `⚠️ 模板版本变了？` 并跳过，不做盲替换）→ 设计正确。
**这是相对于其他队伍的实打实优势**，也是提交二 0/86 的第二重解释（骨架级产物连 DB 层都用不了）。

## 四、reasoning 87% 是头号成本项，但它现在**没有旋钮**

- 事实：reasoning 59,972 / 输出 68,531（§6）＝ **87%**；全量口径 68,941 / 103,847 ＝ **66%**。
- 现状：`llm.py` 只暴露 `temperature`（0.2）与可选 `max_tokens`，**没有任何抑制 reasoning 的开关**。
- **建议登记为下一个便宜实验**（同一个 1 需求样本即可，一次约 10 万 token）：
  ① 换模型族（`glm-5.3-flash` / `kimi-k2.7-code-highspeed`）看 reasoning 占比；
  ② 看网关是否认 `reasoning_effort` 一类的参数；
  ③ `max_tokens` 是**总 completion 上限**（含 reasoning）→ 它省 token 的代价是正文被截断，要成对测。
  度量口径用 **token / 通过条数**，不是 token 绝对值——否则"省 token 换掉通过率"会被记成收益。
