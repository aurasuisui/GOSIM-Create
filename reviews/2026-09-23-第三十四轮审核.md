## 二、我复核（含**我自己的更正**）

### 2.1 判据到底要哪一族：我把链走完了

```
REQ-2.2.spec.ts:  await h.ensurePasswordLogin(page)
  └ helpers.ts:598 ensurePasswordLogin
      ├ 599 openLoginPage(page)
      ├ 600 clickIfVisible(page, [/账号登录/, /password login/i])      ← 命名族
      └ 601 expectPasswordLoginForm(page)
          └ 590-596 expectAnyVisible(page, [
                [/邮箱.*用户名.*手机号/, /email.*username.*mobile/i, /account/i],
                [/密码/, /password/i],
                [/登录/, /^login$/i, /sign in/i]])
              └ 431 expectAnyVisible → 433 expectVisible(scope, value)
                  └ resolveNamed → namedLocators（**8 个 role + 第 9 位 `getByText`**）
```
**产物侧**：`%TEMP%/ctrip2/app/frontend/src/pages/LoginPage.tsx:11` = **`<p>邮箱/用户名/手机号</p>`**
→ `getByText(/邮箱.*用户名.*手机号/)` **命中** ✔（`.*` 匹配那三个分隔符）。

→ **结论：③ 的"预测通过"正确** ✔ —— **我之前那条"`fieldLocators` 不认 `<p>` → 会挂"的推理是错的**：
`fieldLocators`（`getByLabel` / `getByPlaceholder` / `textbox|searchbox|combobox|spinbutton`）
是 **`fillPasswordLogin`**（`:619` 里那处 `fillField`）用的，而 `REQ-2.2` 走的是
**`expectPasswordLoginForm`（命名族）**。**两族的消费方不同，不能混读。**

> **教训（我自己的，记下来）**：我读到 `fillField → resolveField → fieldLocators` 就准备下"会挂"的结论，
> **只差一层没走**（真正的消费方是另一个 helper）。这与"用行号推控制流"是同一个错型的**新形态**：
> **判据要哪一族，必须从"真正消费它的那个 helper"推导，不能从同文件里长得像的那条链推导。**

### 2.2 真问题：**正则源码被当逐字字面量注入**（🟡，不影响本轮判分）

`%TEMP%/ctrip2/gen.log:81` 实际注入：
```
['账号登录', '邮箱.*用户名.*手机号', 'email.*username.*mobile', 'account', '密码', 'password', 'password login']
```
- **L1 的契约永远不可能满足**：`'邮箱.*用户名.*手机号'` 是一条**正则体**，L1 却按**逐字字面**去找
  → 闭环 3 轮全 ❌（`b993c02` 已正确指出"L1 的 ❌ 与判据的目标不是同一件事"），
  **其中约 2 万 token（33,069 里）花在追一个不可能出现的字面串上**。
- **还有一个活的风险**：brief 说"逐字兑现" → 模型**有可能把 `邮箱.*用户名.*手机号` 原样渲染进 UI**
  （本轮它没这么干，而是渲染成 `邮箱/用户名/手机号` ✔——但那是运气/理解，不是机制保证）。
- `final_l1=False` 会写进记录 → 下游读者会以为"这个产物没过 L1"，而其实判据可能通过。

**建议修法（属方案会话定，不阻塞本轮）**：
1. **注入时按形态分流**：正则体的靶子 → 注入**它的字面词元**（`邮箱`/`用户名`/`手机号`）+ **按序/同元素**约束，
   而不是注入正则源码；纯字面靶子 → 照旧逐字注入。
2. 或 **L1 侧识别"形态"**：对正则体契约用**同一条可命中性判据**（与 `③` 共用一套），别用字面子串。
   （两者取一即可；**别两头都改**，否则"两处各编一遍"。）

### 2.3 下一步一句提醒（给方案，不阻塞）

`②`/`③` 与落点约束应当**族感知**：同一份 spec 里既有命名族（`expectVisible/clickIfVisible/countVisibleNamed`）
又有字段族（`fillField/clickField`）→ 同一个串在两类里要求的落点**不同**。
建议 `③` 的输出与回灌清单**每条都带"消费方 helper + 所属族"**（现在 `③` 已带 helper 名 ✔，
只差把"族"显式化），这样落点约束才能写准。
