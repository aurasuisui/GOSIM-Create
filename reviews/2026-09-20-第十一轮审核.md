## 二、要补的三条

### 2.1 🔴 把"本地跑官方测试打我们自己的应用"写进 M3b-1（**决定 6 个 app 能不能迭代得动**）

- **现状**：`PLAN.md` 里 `--target-url` 只出现在**打 12306 参考实现**的上下文（`:974` 一带）；
  M3b-1 的闸门里没有任何"在哪验"的条目，只有一句"产物修补效果**只能在平台上验证**"。
- **问题**：M3b-1 的目标是 **6 个独立的通过率地板**（"6 个都非零"），也就是 6 组
  「生成 → 构建 → 起服务 → 跑测试 → 定向修复」的循环。**如果唯一测试场地是平台**，
  每一轮都要：用户上传 + 逐任务点选 + 吃配额 + 等待。**用户会成为吞吐瓶颈**，而 M3b-1 恰恰最需要多轮迭代。
- **本地已经具备条件**：6 个 app 的官方测试都在 `repos/arc-bench/arc-bench/webapp/<app>/tests/`，
  runner 支持 `--app X --target-url <我们的应用>`；`docs/10 §八` 已经写明了同类做法
  （把 spec 复制进一个有 `@playwright/test` 的项目里跑）。**这是接线，不是新能力。**
- **建议**：M3b-1 的第一条闸门改成
  「**每个 app 都能在本地用官方测试打分**（生成 → 起服务 → `npm run test -- --app X --target-url` → 出 RunRecord）」，
  并且沿用既有纪律（**静置条件 + `load_snapshot` + 每轮重置库**，`docs/04` §三）。
  平台提交从此变成"本地过线后的确认"，而不是"用来试"。
- 顺便：这条也把 **V-6 的验证**变便宜了（本地先做出"部分通过"，再跑一次平台确认口径）。

### 2.2 🟡 M3b-0 的出口判据**在它自己调过的样本上测** → 加一个 held-out 检查

- **现状**：M3b-0 的出口是"**同一 1 需求样本**上零人工构建成功 + ≥4/6"。
- **风险**：M3b-1 真正会踩的坑是**样本特异化**——比如某条修复规则认的是 `RegisterPage` / `onRegistered`
  这种只在这个样本里出现的特征。**在调过的样本上 4/6 全绿，不代表换一个需求还成立。**
- **建议（廉价）**：M3b-0 通过后，**代码一行不改**，换一个单需求样本再跑一次
  （`example/ticketbooking-demo` 的一个叶子，或某个 app 里最小的一条 REQ），
  **判据只要"零人工构建成功"**——通过率可以低（那是能力问题，不是闭环问题）。
  一次约 10 万 token，换的是"M3b-1 不会在铺到第 3 个 app 时才发现闭环过拟合"。

### 2.3 🟡 **每个 app 的 token 上限**没写，而 M3b-1 正是 token 爆炸处

- **现状**：§4.3 的墙钟预算 + 降级有；**token 预算没有**。而 M3b-1 的闸门自己写着
  "模型/成本口径已标定 —— 不能跳过，因为 M3b-1 是 token 量爆炸的地方"。
- **量级参照**：M3a 一个需求 ≈ **10.4 万 token**（`runs/20260920T-m3a-metrics.jsonl`）。
  按分块外推，一个 86 模块的 app 是 **百万级**，6 个 app 是**数百万到千万级**——
  而**配额上限至今未知**（V-5/V-6）。在未知配额下铺开，风险是"铺到一半没额度了"。
- **建议**：M3b-1 加一条「**每个 app 的 token 上限（配置项）+ 到额降级**」，
  照 §4.3 的看门狗模式（到额就收，降级为"至少一个场景端到端可走通"）。
- **附带把两处成本口径补上**（因为"标定"要拿它当基线，标定在错数上就是白标）：
  - `docs/10 §6` 的成本表与记录不符：表写"5 次 / 89,948"，`metrics.jsonl` 是
    **6 条 / 103,847（reasoning 68,941）**，差额 **13,899 = 2,702 + 11,197**（两次 design；
    其中一次 `out=556` 而 `reasoning=556`，正文 0 字 —— 正是 `llm.py:140` 那条"推理吃光输出"的实例）。
    按 `PLAN §4.4` 自己的规则应记两栏：**成功路径 89,948 / 含失败尝试 103,847**。
  - `metrics.jsonl` **缺 `endpoint` 字段**：§6 自己测出同一个"只回两个字"的调用
    比赛网关计 **97**、DeepSeek 官方计 **10**（十倍口径差）。本地迭代改用官方 API 是合理的，
    但记录必须能分辨哪条走哪个表，否则标定出的数字对不上 `pass/CNY`（榜单口径）。
